# 32-B (2026-08-01): 용량 경계 확증 — 세션 B(Phase 3)

> **이 문서는 세션 B의 산출물이자 32번의 최종 판정이다.**
> [32-A 결과](32-2026-08-01-capacity-boundary-session-a.md)의 **3분 hold 임시 경계를 뒤집는다.**

## 결론

> **`Server4 / DB8 / N=8` 구성에서 이 워크로드로 10분 hold를 돌렸을 때 전 항목 100%/0건을
> 만족한 최고 합산 VU는 500이다.** 합산 750은 만족하지 못했다.
>
> **이 워크로드와 현재 구성에서 유한 실행으로 검증된 최고 VU = 500** (10분 hold, 2회 반복 통과).
> **750은 10분 hold 1회 실패** — runbook의 고정 분기에 따라 평균 없이 탈락시켰다.

**32-A의 "750 통과"는 hold가 3분이라 나온 값이다.** 750의 셰딩은 **hold 4.2~4.4분 사이에 시작한다**
(15초 스냅샷 해상도의 경계 구간). 3분 hold는 포화 지점 직전에 끝난다. 32-A는 오측이 아니라 **관측 창이 짧았던 것**이고,
runbook이 판정 정의를 10분 hold × 2회로 잡아 둔 이유가 그대로 확인됐다.

**더 중요한 발견은 따로 있다 — 이 워크로드는 고정 VU에서 10분 안에 정상 상태에 도달하지 않는다.**
부하가 일정한데도 **작업당 정산 실행 시간이 hold 동안 계속 오른다**(750에서 9.19ms → 23.75ms).
배치 크기는 평평하므로 **파편화는 원인이 아니다.** **그 이상은 확정되지 않았다** —
[원인 후보](#고정-부하에서-정산-비용이-오른다--관측은-확정-원인은-미확정)를 좁히지 못했다.
따라서 **"최고 검증 VU"는 hold 길이와 분리되지 않는다.** 아래 [한계](#한계)에 명시한다.

**즉 "500이 몇 분에 실패한다"는 아직 측정된 사실이 아니다.** 측정된 사실은
**"500에서도 같은 상승 추세가 있고 10분 안에는 실패하지 않았다"** 까지다.

## 고정 부하에서 정산 비용이 오른다 — 관측은 확정, 원인은 미확정

Run 1의 hold 구간을 1분 버킷으로 분해했다. **부하(VU)는 내내 일정했다.**

| hold 분 | 작업당 실행 시간 | DB attempt 시간 | 배치 크기 | 체결/s |
|---|---|---|---|---|
| 0.9 | **9.19ms** | 10.98ms | 2.417 | 583.5 |
| 2.9 | 11.79ms | 11.06ms | 2.439 | 587.2 |
| 4.9 | 17.86ms | 14.59ms | 2.628 | 522.5 |
| 6.9 | 20.24ms | 14.71ms | 2.657 | 462.1 |
| 9.9 | **23.75ms** | 15.23ms | 2.688 | 396.8 |

- **작업당 정산 실행 시간이 2.6배**로 오른다(9.19 → 23.75ms).
- **배치 크기는 2.42 → 2.69로 사실상 평평하다.** 29·30·31번에서 확인된 2.76~2.79 범위와 같다 —
  **배치 파편화는 원인이 아니다**(네 번째 독립 반증).
- DB attempt 시간은 1.4배(10.98 → 15.23ms)만 오른다. 작업당 비용이 더 크게 오른 만큼은
  큐잉·경합 몫이다.

같은 구간에 원장도 커졌다 — Run 1은 10분에 `orders` 546,783행 · `ledger_entries` 1,886,343행 ·
`trades` 311,207행을 쌓았고, DB CPU median은 **85%**(p95 92 / max 95)까지 올라갔다
(32-A의 750 3분 실행에서는 median 32.5).

### 확정된 것과 확정되지 않은 것

**확정:**

- 고정 VU인데 **작업당 정산 실행 시간이 9.19 → 23.75ms**로 올랐다
- **DB attempt 시간이 10.98 → 15.23ms**로 올랐다
- **DB CPU와 worker busy도 함께 올랐다**
- **10분 안에 정상 상태에 도달하지 않았다**
- **배치 파편화는 원인이 아니다**(배치 크기가 평평하다)

**미확정 — 아래 어느 것도 이번 세션으로 배제되지 않았다:**

| 후보 | 왜 남아 있나 |
|---|---|
| 원장 크기(행 수) | **원장이 커진 것은 사실이지만 그것이 원인이라는 증거는 없다.** 시간이 흐르면 같이 커지는 양은 여럿이다 |
| 인덱스 | 인덱스 정의·사용량을 조사하지 않았다 |
| WAL·checkpoint·autovacuum 등 쓰기 비용 | 계측하지 않았다 |
| 동일 사용자 지갑의 행 락 경합 | lock wait를 계측하지 않았다 |
| terminal/trade job 구성 변화 | job 종류별 실행 시간을 분리하지 않았다 |
| 오더북 상태 변화 | 매칭 쪽 비용 변화를 분리하지 않았다 |
| **더 오래 돌리면 평형점에 도달하는지** | 10분까지만 봤다. **"정상 상태가 없다"가 아니라 "10분 안에는 없었다"** 가 정확하다 |

> **⚠ 이 문서에 "원장 성장 때문이다"라고 쓰지 않는다.** 상관을 인과로 옮겨 쓰는 것이고,
> 정산 경로는 INSERT·UPDATE·행 락·COMMIT·WAL이 중심이라 **읽기 쿼리 계획만으로는 닫히지 않는다.**
> 진단 설계는 [다음에 볼 것](#다음에-볼-것-이-세션-범위-밖)에 적었다.

### 소요 시간 — 32-A의 17.5분은 사용자 수 때문이다

| 실행 | 사용자 | 체결 | 리컨실리에이션 소요 |
|---|---|---|---|
| 32-A 계단식 | 4,000 | 362,654 | **약 17.5분** |

| 32-B 500 Run 2 | 500 | 240,408 | **31초** |
| 32-B 500 Run 3 | 500 | 241,170 | **9초** |

362,654건인 32-A 계단식은 17.5분이었다 — 체결은 1.17배 차이인데 시간은 35배 차이고,
사용자는 750 대 4,000이다.

32-A는 이 현상을 관측하면서 **"초선형이라고 확정하지 않는다"고 유보**했고, 체결 수·사용자 수·
주문 수·오더북 상태가 모두 달라 통제되지 않았다고 적었다. **그 유보는 옳았다.**
32-B의 세 실행은 체결 수가 240k~311k로 비슷한데 사용자 수도 500~750으로 같이 낮아
**둘을 분리하지는 못했지만**, 체결이 더 많은 750 실행이 32-A 계단식보다 35배 빨랐다는 사실은
**체결 수 단독 설명을 배제한다.** 원인 규명은 여전히 별도 진단 항목이다.

세션 B의 시간 예산 판단(17.5분 이상)은 결과적으로 과했다 — 세 실행 모두 31초 이내였다.

## 한계

- **유한 테스트다.** "영원히 100%"가 아니라 **측정 조건에서 실패 0건이었던 최고 검증 VU**다.
- **⚠ 숫자가 hold 길이와 분리되지 않는다.** 이번 세션의 핵심 발견이다. 부하가 일정해도
  작업당 정산 비용이 계속 오르고 **10분 안에 정상 상태에 도달하지 않았다**(원인 미확정).
  750은 3분에 통과하고 10분에 실패했다. 500도 **10분에 통과했을 뿐**이고, 같은 상승 추세가
  그대로 보인다. **"500 VU를 무한히 버틴다"는 뜻이 아니다.** 20분·60분 hold는 다른 숫자를 낼 것이다.
  **다만 500이 몇 분에 실패하는지는 외삽했을 뿐 측정하지 않았다** — 시점을 인용하지 않는다.
  **"정상 상태가 존재하지 않는다"고도 쓰지 않는다** — 더 오래 돌리면 평형점에 도달하는지는
  측정하지 않았다.
- **workload-specific이다.** 주문 혼합·취소 비율·think time이 달라지면 숫자도 달라진다.
- **깨끗한 DB에서 시작한 결과다.** 매 실행 10개 테이블 TRUNCATE 후 시작했다. **원장이 이미 큰
  환경에서 이 숫자가 어떻게 달라지는지는 측정하지 않았다** — 비용 상승의 원인이 확정되기 전에는
  "더 낮은 VU에서 셰딩이 시작된다"고 단정할 수 없다.
- **해상도 250 VU.** 500과 750 사이는 측정하지 않았다.
- **run-to-run 분산**: 처리율 계열은 500 2회에서 +0.2~1.1%로 재현됐다. **지연 p95는 약 35% 분산**이
  확인돼 있어 판정에 쓰지 않았다.
- **Run 1의 드레인 소요 시간을 측정하지 못했다.** k6 종료 후 약 42분 뒤에 확인해 `outstanding=0`만
  확인했다. 500 두 실행은 종료 직후 첫 확인에서 0이었다.
- **VM 호스트 분산**은 분리하지 않았다.

## 다음에 볼 것 (이 세션 범위 밖)

### 1. 고정 부하에서 정산 비용이 상승하는 원인 진단 — **최우선**

이번 세션이 새로 연 가장 큰 항목이다. 두 단계다.

**(a) 정적 DB 조사** — DB VM 한 대로 끝난다.

- 테이블·인덱스 크기, **실제 인덱스 정의와 사용량**(`pg_stat_user_tables` / `pg_stat_user_indexes`)
- **autovacuum·dead tuple·checkpoint·WAL** 통계
- 정산 SQL의 **`EXPLAIN (ANALYZE, BUFFERS, WAL)`**
- 가능하면 `pg_stat_statements`의 **호출당 시간**

명백한 missing index나 write amplification 후보를 찾는 단계다.

**(b) 정산 트랜잭션 크기 스윕** — **최소 드라이버가 필요하다.**

깨끗한 DB와 단계별 사전 적재 DB에서 **실제 `SettleTradeBatch`** 를 반복한다.

| 축 | 수준 |
|---|---|
| DB 크기 | 초기 / 중간 / **32-B 종료 규모** |
| 동시성 | **N=1 / N=8** |
| 고정 | batch 크기 · 사용자 분포 · 주문 유형 |
| 관측 | attempt latency · job latency · **lock wait** · **WAL** · CPU |

**판정이 명확하게 갈린다.**

| 결과 | 지목되는 원인 |
|---|---|
| **N=1부터** DB 크기에 따라 느려짐 | 인덱스 · WAL · 쓰기 증폭 |
| **N=1은 평평, N=8만** 느려짐 | **락 · 동시성 경합** |
| 둘 다 평평 | 32-B의 오더북 · job mix · 사용자 상태 변화 |

> **⚠ "부하 테스트가 필요 없다"가 아니다.** load-gen 2대와 전체 k6 세션은 필요 없지만,
> **실제 트랜잭션을 실행하는 통제된 부하는 필요하다.** `EXPLAIN`만으로는 닫히지 않는다 —
> 정산 경로의 중심은 INSERT · UPDATE · 행 락 · COMMIT · WAL이고 `EXPLAIN`은 읽기 계획만 잘 보여준다.

### 2. `N=16` — **조건부**

**위 진단이 동시성 부족을 가리킬 때만 간다.** 750 실패 시점에 **DB CPU median 85 / p95 92**였고,
원인이 **락이나 WAL이면 N=16은 개선이 아니라 지연 악화를 만들 수 있다.**
32-A의 "N=16이 먼저" 판단은 **DB CPU 여유가 있다는 3분 관측에 근거했으므로 무효**다.
서버 VM 증설도 우선순위가 아니다.

### 3. 리컨실리에이션 실행시간 — **독립 항목**

**정산 비용 상승과 섞지 않는다.** 리컨실리에이션은 사용자·지갑별 LATERAL 집계라는 **별도 쿼리**이고,
정산 경로(INSERT·UPDATE·락·COMMIT)와 비용 구조가 다르다. 원인 미확정 진단 백로그로 따로 둔다.
