# 30번 (2026-07-31): 정산 동시성 스윕 N=4 → 8 GCP 통제 비교

## 요약(먼저 읽어야 할 것)

- **N=4가 29번을 6개 지표 전부 허용 오차 안에서 재현했다**(최대 편차 −0.9%). 같은 구성의
  run-to-run 분산을 처음 측정한 것이며, **단일 실행 A/B 비교가 성립한다**는 뜻이다.
- **N=8은 처리율을 올렸다**: hold 구간 정산 처리율 **368.35 → 467.29 trades/s(+26.9%)**,
  업무 성공률 **22.43% → 26.62%(+4.19%p)**, 전체 체결 **137,265 → 163,836건(+19.4%)**.
- **그러나 N=8은 안전 게이트를 통과하지 못했다.** `sli_order_response_availability`가
  **100.00% → 99.94%** 로 떨어졌다(1,079,484건 중 **568건이 1초 계약을 초과**). N=4는
  1,071,434건 중 **0건**이었다. runbook의 "안전이 성능보다 먼저" 규칙에 따라 **N=8은 기각**한다.
  결론의 범위는 **"N=8 자체가 나쁘다"가 아니라 "현재 DB 4 vCPU 구성에서는 N=8의 처리율 이득이
  응답 가용성 계약을 깨므로 채택할 수 없다"** 이다 — 그 이득을 안전하게 회수할 수 있는지가 31번의 질문이다.
- **정합성은 양쪽 다 무결**했다 — 위반 0, fallback 0, quarantine 0, duplicate terminal 0,
  `sli_cancel_success` 100%, 5xx 0건. 깨진 것은 정합성이 아니라 **지연 하드 보장**이다.
- **먼저 벽에 닿은 것은 DB CPU다.** hold 구간 DB `us+sy` max/p95/median이
  **72/61/50 → 88/84/77**, recovery에서는 **99/99/92.5**. `wa`는 ≤9, `st`는 ≤2로
  스토리지·호스트 경합이 아니라 **실제 CPU 소모**다. 서버는 67/65/64 → 77/76/72.5로 여유가 남았다.
- **초기 풀 고갈은 N=8에서 악화되지 않았다.** 29번이 지목한 setup 구간의 누적 대기는
  `wait_count` 26,676 → 26,648(−0.1%), `wait_duration` 13,966 → 14,645초(+4.9%)로 사실상 동일하다.
  부하 스테이지(ramp·hold·recovery) 구간의 풀 대기 델타는 **양쪽 모두 0**이었다.

"유력한 설명"이지 증명은 아니다.**

## 판정

| 항목 | 결과 |
|---|---|
| N=4 기준선 재현 | ✅ 6개 지표 전부 허용 오차 내 — A/B 비교 성립 |
| N=8 정합성 | ✅ 무결(위반 0 · fallback 0 · quarantine 0 · duplicate 0 · 취소 100%) |
| **N=8 안전 게이트** | ❌ **실패** — `sli_order_response_availability` 100.00% → 99.94% |
| N=8 처리율 | ✅ hold +26.9%, 업무 성공률 +4.19%p, 전체 체결 +19.4% |
| N=8 램프 풀 고갈 | ✅ 악화 없음(setup `wait_count` −0.1%) |
| 병목 이동 | **정산 워커 → DB CPU**(hold `us+sy` p95 84, recovery 99) |

**runbook의 "안전이 성능보다 먼저" 규칙에 따라 N=8은 기각한다.** 처리율 이득은 실재하지만
응답 가용성 하드 보장이 깨졌고, 그 원인으로 지목되는 DB CPU는 이미 recovery에서 포화에 근접했다.

> **결론의 정확한 범위**: 이 측정이 말하는 것은 **"N=8 자체가 나쁘다"가 아니다.**
> **"현재 DB 4 vCPU 구성에서는 N=8의 처리율 이득이 응답 가용성 계약을 깨므로 채택할 수 없다"** 이다.
> N=8의 이득(+26.9%, 업무 성공률 +4.19%p)은 실재하며, **DB를 키운 뒤 그 이득을 안전하게
> 회수할 수 있는지가 다음 실험의 질문**이다.

**다음 표적은 락 경합이 아니다.** N=8에서 데드락·재시도·fallback 로그가 전부 0건이었고
`st`·`wa`도 낮다. 관측된 신호는 **DB의 CPU 용량**을 가리킨다.

### 31번은 2단계여야 한다

**`N=4 + DB 8 vCPU급` 한 번만으로는 가설을 검증할 수 없다.** N=4는 이미 worker가 포화
(busy 99.97%)인 반면 DB CPU에는 여유가 있었으므로(hold `us+sy` p95 61), **DB만 키워도 처리율이
거의 안 변할 수 있다.** 그 결과로 DB 증설 가설을 기각하면 오판이다.

| 단계 | 구성 | 목적 |
|---|---|---|
| **1** | `N=4` + DB 8 vCPU급 | **DB만 바꾼 안전 기준선.** 기존 N=4 대비 회귀 여부와 DB attempt 지연 변화를 확인한다. **개선이 작아도 가설을 여기서 기각하지 않는다** |
| **2** | `N=8` + DB 8 vCPU급 | **실제 가설 검증.** 같은 DB에서 N만 바꿔 ① 1초 초과 568건이 다시 0이 되는지 ② N=8의 처리율 이득을 안전하게 회수하는지 |

**1단계의 안전 게이트를 통과한 경우에만 2단계로 간다.**

> **⚠ 이것은 "DB CPU 단독 실험"이 아니다.** `e2-highcpu-4 → e2-highcpu-8`은 vCPU와 함께
> **메모리도 증가**하므로 엄밀히는 **DB 인스턴스 크기 실험**이다. CPU만 분리하려면 동일 메모리의
> custom machine type이 필요하다. 그렇게 하지 않는다면 **표현을 "DB CPU 증설"이 아니라
> "DB 인스턴스 4→8 vCPU급 증설"로 낮추고 RAM 증가량도 함께 기록**해야 한다.
>
> **15번의 2.46배(2→4 vCPU)는 가능성을 지지하는 선례일 뿐 이번 결과의 예상 배율이 아니다.**
> 그때는 병목 구조가 달랐다.

## 한계

- **재현 게이트는 지연을 포함하지 않았다 — 지연의 run-to-run 분산은 처리율보다 크다.**
  Phase 1 게이트 6개 지표는 처리율·업무 성공률·큐 상태였고 **응답 지연이 빠져 있었다.**
  실제로 **동일 구성·동일 바이너리**인 29번과 이번 N=4의 `http_req_duration` p95는

  | | 29번 | 30번 N=4 | 차이 |
  |---|---|---|---|
  | p95 (A) | 120.55ms | 162.1ms | **+34.5%** |
  | p95 (B) | 120.40ms | 163.2ms | **+35.6%** |

  **약 35% 차이**났다. 업무 성공률이 22.70% → 22.43%로 거의 같아 **구성 효과로 설명되지 않는다.**
  즉 이번에 처음 측정한 run-to-run 분산은 **처리율에는 적용되지만 지연에는 적용되지 않는다.**

  **다만 N=8 기각은 이 분산에 영향받지 않는다.** 기각 근거는 p95가 아니라 **1초 초과 건수**이며,
  그 값은 **29번 0건 / N=4 0건으로 두 번 정확히 재현된 뒤 568건으로 증가**했다(각각 약 107만 건
  중). 두 번 연속 정확히 0이던 지표가 뛴 것이므로 분산으로 설명되지 않는다.

  **향후 지연 기반 판정(31번의 DB 증설 포함)에는 이 분산 폭을 먼저 정해야 한다.**
  현재로서는 **p95 단독 비교로 개선/회귀를 주장할 수 없고**, 1초 초과 건수처럼 계약에 직결된
  지표를 근거로 삼아야 한다.
- **N=4 실행의 리컨실리에이션(ledger_wallet·asset_conservation)은 그 실행의 최종 데이터에
  대해 돌리지 못했다.** `ReconciliationWorker`의 기본 주기가 1시간이라 재기동으로 1회 강제
  실행해야 하는데, N=8 준비 과정에서 **TRUNCATE 후에** 재기동이 일어나 빈 DB를 검사했다.
  N=4 쪽 근거로 남은 것은 `failed_settlements`/`failed_market_completions`/
  `failed_order_cancellations` 0 · 잔존 시장가 0 · outbox PENDING 0 · `reconciliation_violations`
  테이블 0행이며, **동일 구성·동일 바이너리의 29번은 전체 리컨실리에이션을 통과**했다.
  N=8은 최종 데이터에 대해 정상적으로 1회 완주시켜 4항목 전부 0을 확인했다
  (`reconciliation_last_run_timestamp_seconds = 1785441264`, 재기동 이후 값).
- **시작 skew 산출 방법 정정(29번 수치에도 적용)**: 29번은 skew를 `k6 프로세스 시작 시각 +
  progress 라인 elapsed`로 계산해 0.201초로 적었다. 그러나 **k6의 elapsed는 프로세스 시작이
  아니라 초기화 이후부터 센다.** 이번 N=4에서 같은 계산이 A −0.4초 / B −1.7초, 즉
  **배리어보다 이른 시각**(물리적으로 불가능)을 내놓아 드러났다 — B의 `ulimit -n`이 4배
  (1,048,576 vs 262,144)라 k6 init이 그만큼 길었던 것이다. **실제 정렬 근거는 배리어**
  (공통 절대 epoch까지 `sleep`, 미달 시 throw — 네 실행 모두 throw 없음)**와 VM 시계 차이
  ≤0.04초**다. 29번 문서의 "0.201초"도 같은 이유로 init 시간이 섞인 값이니 그대로 인용하지 말 것.
- **run-to-run 분산 표본은 2회뿐**이다(29번·30번 N=4). 허용 오차 ±10%는 이 2회에서 사후
  확인된 것이지 통계적으로 유도된 값이 아니다.
- **568건의 1초 초과를 요청 단위로 추적하지 않았다.** DB CPU가 유력한 설명이지만, 어떤 요청이
  어디서 느려졌는지는 이번 계측(구간 집계)으로 확정할 수 없다.
- **`settlement_job_execution_seconds`가 batch job과 terminal job을 구분하지 않는다**(29번과 동일).
  hold 기준 worker busy 99.96% 중 batch DB 작업은 43.82%이고 나머지는 terminal job이다.
- **스냅샷 해상도 15초**: 구간 경계가 목표 대비 N=4 −6.1초 / N=8 +6.3초 이동했다. 두 실행의
  구간 길이(180.3s vs 180.4s)는 사실상 동일해 비교에는 영향이 없다.
- **CPU는 `vmstat` 5초 표본**이므로 5초보다 짧은 스파이크는 잡히지 않는다.
