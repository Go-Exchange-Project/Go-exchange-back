# 31번 (2026-07-31): DB 인스턴스 4→8 vCPU급 증설 + 정산 동시성 N=4/8 통제 비교

## 요약(먼저 읽어야 할 것)

- **DB8/N8이 1차 안전 게이트와 2차 효과 게이트를 모두 통과했다 — 채택 후보다.**
  30번에서 DB4/N8을 기각하게 만든 **1초 계약 초과가 568건 → 0건**이 됐고, 그 상태에서
  DB8/N4 대비 hold 처리율 **+33.9%**, 업무 성공률 **+5.54%p**를 얻었다.
- **runbook의 예상이 빗나간 지점이 하나 있다.** "N=4는 이미 worker 포화라 DB만 키워도 처리율이
  거의 안 변할 수 있다"고 적었지만, **DB8/N4만으로도 hold 처리율이 368.35 → 480.92 trades/s
  (+30.6%)** 로 올랐다. worker busy는 99.94%로 여전히 포화지만 **attempt 시간이 14.19 → 10.59ms
  (−25.4%)** 로 줄어 같은 포화 상태에서 더 많이 처리했다. 그 결과 **DB8/N4가 이미 30번
  DB4/N8(163,836 trades)을 체결 수에서 넘어섰다**(167,128).
- **네 실행 전부 정합성 무결**: 위반 0, fallback 0, quarantine 0, duplicate terminal 0,
  `sli_cancel_success` 100%, 5xx 0건. **두 실행 모두 그 실행의 최종 데이터에 대해 리컨실리에이션을
  완주**시켜 4항목 0을 확인했다(30번에서 놓친 항목을 이번엔 양쪽 다 확보했다).
- **병목이 DB CPU에서 서버 CPU로 이동했다.** hold `us+sy` max/p95/median — DB는
  **88/84/77(30번 DB4/N8) → 51/49/41(DB8/N8)** 로 크게 내려갔고, 서버는
  **77/76/72.5 → 86/85/83** 으로 올라 이제 서버가 가장 바쁘다. `wa` ≤5, `st` 0.
- **풀 크기 25는 여전히 제약이 아니다.** 부하 구간 `in_use` 최대 12/25. setup 구간의 누적 대기
  (~26.4k)는 DB 증설로도 거의 안 변했다 — **그 대기는 DB 속도가 아니라 풀 상한과 계정 생성·펀딩
  버스트의 관계**에서 나온다.

### 선행 신호 — 지속 부하(hold)에서 처음 관측된 풀 대기

DB8/N8의 **hold 구간에 `wait_count` 83건(0.70s)** 이 나타났다. **hold에서 관측된 것은 처음**이다
(DB8/N4는 0, 30번은 DB4/N4·DB4/N8 모두 hold 0).

**다만 "부하 구간 최초"는 아니다** — 30번 burst에서 이미 DB4/N4 61건, DB4/N8 203건이 있었다.
그리고 이번 **burst는 36건으로 30번보다 오히려 줄었다**(203 → 36). 따라서 burst 수치를 hold 신호와
같은 신규 현상으로 묶으면 안 된다.

**의미**: 절대량은 무시할 수준(0.70s)이지만, **스파이크가 아닌 지속 부하에서 풀 대기가 처음 생겼다**는
점에서 **N을 더 올릴 때 먼저 커지는지 지켜봐야 할 선행 신호**다. 현재로서는 제약이 아니다.

## CPU — 병목이 DB에서 **서버**로 이동했다

max / p95 / median:

| VM | 구간 | 지표 | 30번 DB4/N8 | DB8/N4 | DB8/N8 |
|---|---|---|---|---|---|
| **server** | hold | **`us+sy`** | 77 / 76 / 72.5 | 73 / 73 / 71 | **86 / 85 / 83** |
| | burst | `us+sy` | 86 / 86 / 78 | 84 / 84 / 77 | **90 / 90 / 86** |
| | 전 구간 | `wa` · `st` | 0 · 0 | 0 · 0 | **0 · 0** |
| **db** | hold | **`us+sy`** | **88 / 84 / 77** | 30 / 27 / 24 | **51 / 49 / 41** |
| | burst | `us+sy` | 82 / 82 / 74 | 27 / 27 / 24 | **69 / 69 / 65** |
| | recovery | `us+sy` | **99 / 99 / 92.5** | 45 / 43 / 38 | **85 / 49 / 44** |
| | 전 구간 | `wa` | ≤6 | ≤4 | **≤5** |
| | 전 구간 | `st` | ≤2 | 0 | **0** |

**30번에서 벽이었던 DB CPU가 내려갔다** — hold p95 84 → 49, recovery p95 99 → 49.
대신 **서버 CPU가 hold p95 85·median 83, burst p95 90으로 올라 이제 가장 바쁘다.**
`wa`는 여전히 ≤5, `st`는 0이므로 스토리지·호스트 경합은 아니다.

이것이 **DB8/N8에서 1초 초과가 0건이 된 이유**로 가장 잘 맞는 설명이다 — 주문 제출 경로가
공유하던 DB가 더 이상 포화가 아니어서 응답이 계약 안에 들어왔다. **다만 요청 단위 인과는
추적하지 않았으므로 "유력한 설명"이지 증명은 아니다.**

## 보고만 하고 판정에 쓰지 않은 것 — 응답 지연

**동일 구성의 run-to-run p95 분산이 약 35%로 확인됐으므로(30번 한계) 판정 기준으로 쓰지 않는다.**
설명용으로만 남긴다(A / B):

| 지표 | DB4/N4(30번) | DB4/N8(30번) | DB8/N4 | DB8/N8 |
|---|---|---|---|---|
| median | 0.75 / 0.86ms | 1.18 / 1.26ms | **0.92 / 0.95ms** | **2.87 / 2.89ms** |
| p90 | 70.7 / 70.5ms | 179.3 / 181.3ms | **46.3 / 46.0ms** | **126.3 / 125.6ms** |
| p95 | 162.1 / 163.2ms | 332.6 / 339.8ms | **77.6 / 77.5ms** | **241.2 / 239.2ms** |
| max | 4.60 / 4.66s | 4.69 / 4.63s | **4.61 / 4.69s** | **4.58 / 4.62s** |
| **1초 초과** | **0 / 0** | **275 / 293** | **0 / 0** | **0 / 0** |

> 업무 성공률이 오르면 셰딩(503, 즉시 응답)의 비중이 줄어 **p90·p95는 구성 효과만으로도 올라간다.**
> 같은 N끼리 비교하면 DB8이 DB4보다 낮다(N=4: 162→78ms, N=8: 336→240ms).

### 채택 관점의 비교 — `DB4/N4 → DB8/N8`

위 same-N 비교는 **DB 증설 효과를 분리**하는 데 쓴다. 반면 **실제 채택 결정은 현재 구성
(DB4/N4)에서 DB8/N8로 가는 것**이므로 그 비교를 따로 남긴다:

| 지표 | DB4/N4(30번) | DB8/N8 | 변화 |
|---|---|---|---|
| 전체 체결 | 137,265 | **205,628** | **+49.8%** |
| 전체 주문 | 240,271 | **360,779** | **+50.2%** |
| business success | 22.43% | **32.05%** | **+9.62%p** |
| **1초 초과** | **0건** | **0건** | 유지 |
| p95 (A/B) | 162.1 / 163.2ms | 241.2 / 239.2ms | **+48%** |

**p95 +48%는 확인된 run-to-run 분산(약 35%)을 조금 넘는 정도의 약한 신호다.** 회귀로 단정할 수도,
무시할 수도 없다. **판정에는 사용하지 않는다** — 채택 근거는 1초 초과 0건과 2차 효과 게이트다.

## 판정

| 항목 | 결과 |
|---|---|
| DB8/N4 회귀 확인 | ✅ 회귀 없음 — 오히려 hold +30.6%, 업무 성공률 +4.08%p |
| **1차 안전 게이트** | ✅ **양쪽 통과 — 1초 초과 0건** |
| **2차 효과 게이트** | ✅ **통과** (+33.9% / +5.54%p, 절대 하한도 충족) |
| 결론 | **DB 인스턴스 증설로 N=8의 처리율 이득을 응답 가용성 계약을 깨지 않고 회수했다 — DB8 + N=8 채택 후보** |
| 새 병목 | **서버 CPU**(hold p95 85 / burst p95 90). DB는 hold p95 49로 여유 |

**결론의 범위**: 이것은 **DB 인스턴스 증설 효과**(CPU + RAM + 호스트 변경)이지 CPU 단독 효과가 아니다.

## 한계

- **DB4 기준값은 다른 세션·다른 DB VM 호스트에서 얻은 값이다.** 머신 타입 변경은 실행 호스트를
  바꾸므로 DB4→DB8 비교에는 **호스트 분산이 섞여 있다.** 이번 설계로 분리할 수 없다.
  다만 **DB8/N4와 DB8/N8은 같은 세션·같은 호스트**에서 연속 측정했으므로 2차 효과 게이트 판정에는
  이 오염이 없다.
- **CPU와 RAM이 함께 증가**했다 — "CPU 증설 효과"가 아니라 **"인스턴스 증설 효과"** 다.
  postgres 설정은 그대로여서 늘어난 RAM은 주로 OS 페이지 캐시로 갔다.
- **지연 p95의 run-to-run 분산이 약 35%** 로 확인돼 지연 개선을 p95로 주장할 수 없다.
  하드 계약(1초 초과 건수)만 판정에 썼다.
- **1초 초과가 0건이 된 요청 단위 인과를 추적하지 않았다.** DB CPU 여유가 유력한 설명이지만
  구간 집계로는 확정할 수 없다.
- **`settlement_job_execution_seconds`가 batch job과 terminal job을 구분하지 않는다**(29·30번과 동일).
  hold 기준 worker busy 99.96% 중 batch DB 작업은 45.51%다.
- **스냅샷 해상도 15초** — 구간 경계가 목표 대비 최대 ±7초 이동했다. 두 실행의 구간 길이는
  180.3s / 180.4s로 사실상 동일해 비교에는 영향이 없다.
- **CPU는 `vmstat` 5초 표본**이라 5초보다 짧은 스파이크는 잡히지 않는다.
- **각 구성을 1회씩만 측정했다.** 처리율 계열은 29·30번에서 재현이 확인됐지만(최대 편차 −0.9%)
  이번 4개 구성 각각의 run-to-run 분산은 측정하지 않았다.
