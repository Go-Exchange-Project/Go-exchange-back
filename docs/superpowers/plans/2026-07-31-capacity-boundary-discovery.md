# 용량 경계 탐색 — 100% 유지 최고 검증 VU (32번)

> **For agentic workers:** 측정 runbook이다. **Phase 0(preflight) → Phase 1(탐색) → Phase 2(정밀화)
> → Phase 3(확증) → Phase 4(판정·문서)** 순서로 체크박스로 진행한다.
> **이 문서는 계획만 담는다 — GCP 실행은 별도 측정 세션에서 수행한다.**

**Goal:** **"가용성·정합성·업무 성공률을 모두 100%로 유지하는 최대 부하는 얼마인가"** 에 답한다.

> **진행 상태 (2026-08-01)**: **완료** — 세션 A(Phase 0~2) + 세션 B(Phase 3) →
> [32-A 결과](../../benchmarks/32-2026-08-01-capacity-boundary-session-a.md) ·
> **[32-B 결과(최종 판정)](../../benchmarks/32-2026-08-01-capacity-boundary-session-b.md)**.
>
> **최종: 이 워크로드와 현재 구성에서 유한 실행으로 검증된 최고 VU = 합산 500**
> (10분 hold, 2회 반복 통과). **750은 10분 hold에서 실패**(업무 성공률 93.48%).
>
> **세션 A의 "3분 hold 750 통과"는 세션 B에서 뒤집혔다.** 750의 셰딩은 hold 약 4분에 시작하므로
> 3분 hold는 포화 직전에 끝난다. 판정 정의를 10분으로 잡아 둔 것이 유효하게 작동했다.
>
> **⚠ 세션 B가 새로 연 항목**: 부하가 일정해도 **작업당 정산 비용이 원장 크기와 함께 오른다**
> (750에서 9.19ms → 23.75ms, 배치 크기는 평평). 즉 **정상 상태가 존재하지 않고, 최고 검증 VU는
> hold 길이와 분리되지 않는다.** 500도 **10분에 통과했을 뿐**이고 같은 상승 추세가 보인다.
> **500이 몇 분에 실패하는지는 측정하지 않았다** — 외삽 시점을 인용하지 않는다.
>
> **⚠ 실행 시 주의(32-A에서 확인)**: `PROFILE=capacity`를 **셸 환경변수로 주면 반영되지 않는다** —
> `k6 inspect`가 기존 6-stage 스파이크를 그대로 돌려준다. 반드시 **`-e PROFILE=capacity`** 로 줘야
> 8 stage와 서브메트릭 threshold가 선언된다.

**판정의 정확한 정의 (이 문서 전체를 지배한다):**

> 현재 `Server4 / DB8 / N=8` 구성에서 **지정된 주문 혼합**으로 **10분 동안** 측정했을 때,
> **응답 가용성 100% · 1초 초과 0건 · 업무 성공률 100% · 취소 인프라 실패 0건 ·
> 정합성·fallback·quarantine 0 · 증가하는 백로그 없음**을 만족한 **가장 높은 합산 VU**.
>
> **유한 테스트이므로 수학적인 "영원한 100%"가 아니다.** **측정 조건에서 실패가 0건이었던
> 최고 검증 VU**라고 표현한다.
>
> **"최대 용량"이라고 쓰지 않는다.** 정확한 표현은
> **"이 워크로드와 현재 구성에서 유한 실행으로 검증된 최고 VU"** 다.

**선행**: [31번 결과](../../benchmarks/31-2026-07-31-db-instance-scaleup.md)(현재 채택 구성) ·
[31번 runbook](2026-07-31-db-instance-scaleup.md)(하니스·절차 원본)

## 현재 확정된 것과 확정되지 않은 것

기존 벤치마크는 **일부러 포화시키는 스파이크 프로파일**이었고, 계단 사이에 측정점이 없다.

| VU (2대 합산) | 상태 |
|---|---|
| **10,000**(hold) | **실패 확정** — 업무 성공률 32.05% |
| 600(회복 구간) | **유력한 통과 후보이나 미확인** — worker busy 39.85%, `2N` 점유 3.4%로 포화가 아닌 것은 맞지만 **구간별 업무 성공률을 계산하지 않았다** |
| 그 사이 | **데이터 없음** |

> **따라서 현재 말할 수 있는 것은 "최대치는 10,000 미만"뿐이고, 정확한 하한은 아직 없다.**
> 600 VU 통과를 기정사실로 쓰지 않는다.

**기존 수치로 외삽하면 안 되는 이유**: 셰딩되면 스크립트가 `Retry-After`만큼 백오프하므로
(`sleep(retryAfter + jitter)`) **포화 상태의 VU당 주문 속도가 인위적으로 낮아져 있다.**
그 값으로 역산한 VU 추정치는 틀린다.

**서버 메트릭으로는 판정할 수 없다:**

- 더 결정적으로, **응답 가용성의 `duration ≤ 1,000ms`는 클라이언트 지표**다.
  서버 메트릭으로 대체할 수 없다.

**현재 k6의 세 SLI는 stage 라벨 없이 전체 실행으로만 집계된다.** 따라서 둘 중 하나가 필요하다:

| 방식 | 쓰는 곳 |
|---|---|
| **k6 SLI에 `vu_level` 태그**를 붙여 단계별 집계 | Phase 1(탐색) |
| **각 VU 후보를 독립 실행**해 전체 summary를 그 후보 결과로 사용 | Phase 2·3(정밀화·확증) |

### 하니스 변경 3가지 (Phase 1 전용)

`_workspace/loadtest/`만 수정한다(**이미 추적 중인 파일이다**). **앱 코드·측정 기준 SHA는 건드리지
않는다** — `git diff 82b4d7f..HEAD -- '*.go'`는 계속 비어 있어야 한다.

#### (1) 8-stage 스케줄이 필요하다 — 기존 `STAGE1~6`으로는 부족하다

`ramp→500→hold→1,000→hold→2,000→hold→4,000→hold`는 **최소 8개 stage**다. 현재 하니스는
`SPIKE_STAGES`가 6개 고정이라 env 오버라이드만으로 표현할 수 없다. 둘 중 하나를 택한다:

| 방식 | 내용 |
|---|---|
| **A. 전용 스케줄 상수 추가**(권장) | `CAPACITY_STAGES`를 8개로 별도 선언하고 `__ENV.PROFILE=capacity`일 때 선택 |
| B. JSON/env 기반 스케줄 | `__ENV.STAGES_JSON`을 파싱해 임의 개수 지원 |

**A가 더 작다** — 기존 스파이크 프로파일을 건드리지 않고 병행할 수 있어 26~31번 재현성이 유지된다.

```
CAPACITY_STAGES = [
  30s→500, 3m@500, 30s→1000, 3m@1000, 30s→2000, 3m@2000, 30s→4000, 3m@4000
]   // 총 14분, 각 값은 load-gen 1대 기준(합산은 ×2)
```

#### (2) `vu_level`은 **요청 시작 시각**으로 고정한다

응답 완료 시각으로 계산하면 **hold 종료 직전에 시작해 다음 ramp에서 끝난 요청이 잘못된 계단에
들어간다.**

```js
const startedAt = Date.now();
const level = levelForElapsed(startedAt - LOAD_START_AT_MS);
const res = http.post(...);
const cls = classifyOrderResponse(res.status, res.timings.duration, RESPONSE_SLO_MS);
orderResponseAvailability.add(cls.available, { vu_level: level });
orderBusinessSuccess.add(cls.businessSuccess, { vu_level: level });
// cancel SLI도 동일하게 요청 시작 시각 기준
```

`levelForElapsed`는 누적 duration과 대조해 `'ramp'` 또는 `'500'`/`'1000'`/… 을 돌려준다.
**`ramp` 태그는 분석에서 제외**한다(hold만 판정에 쓴다).

**단위 테스트가 필요하다** — `sli-classify.selftest.js` 선례를 따라
`_workspace/loadtest/level-classify.selftest.js`를 만들고 **경계 직전·정확한 경계·직후** 세 지점을
고정한다(예: hold 종료 −1ms / 정확히 종료 시각 / +1ms).

#### (3) 1초 초과 건수는 **별도 Counter**로 센다

`sli_order_response_availability`의 fail에는 **느린 응답뿐 아니라 status 0·예상 밖 상태도 섞인다.**
판정 지표가 "`duration > 1,000ms` 0건"이므로 그 값만 따로 세야 한다.

```js
const orderResponseOverSlo = new Counter('sli_order_response_over_slo_total');

if (res.timings.duration > RESPONSE_SLO_MS) {
  orderResponseOverSlo.add(1, { vu_level: level });
}
```

**A·B 각각의 counter가 0인지 확인한 뒤 합산**한다(한쪽만 보면 놓친다).

#### 서브메트릭 노출

태그를 달아도 **threshold 선언이 없으면 summary에 나타나지 않는다.** 항상 통과하는 형태로 둔다:

```js
thresholds: {
  'sli_order_business_success{vu_level:500}': ['rate>=0'],
  'sli_order_response_availability{vu_level:500}': ['rate>=0'],
  'sli_order_response_over_slo_total{vu_level:500}': ['count>=0'],
  // 계단마다 반복
}
```

## 3단계 구조 — 계단식 한 번으로는 확정할 수 없다

**낮은 계단의 주문·오더북·캐시 상태와 백로그가 다음 계단으로 이어진다.** 높은 계단에서 한 번
포화되면 **이후 계단의 결과가 오염된다.** 최종 정합성 0도 **각 계단의 정합성을 개별 증명하지 못한다.**

| Phase | 목적 | 방식 |
|---|---|---|
| **1. 탐색** | 최초 실패 구간을 **빠르게** 찾는다 | stage-tagged 계단식, 넓은 간격 |
| **2. 정밀화** | 최고 통과와 최초 실패 사이를 좁힌다 | **독립 실행**, 이분 또는 250~500 VU 단위 |
| **3. 확증** | 최고 통과 후보를 방어 가능하게 만든다 | **깨끗한 DB에서 독립 실행**, 10분 hold, **최소 2회 반복**. **바로 위 후보도 별도 실행** |

**Phase 1의 결과는 방향 지시일 뿐 판정이 아니다.** 최종 숫자는 Phase 3에서만 나온다.

### Phase 1: 탐색 — 최초 실패 구간 찾기

**계단(2대 합산)**: `500 → 1,000 → 2,000 → 4,000`. 각 hold **3분**, 사이 ramp 30초.

- [x] **Step 1: 실행** — 31번의 캐시 공정성 절차(DB VM 재기동 → TRUNCATE → 서버 재기동 →
  수집기 1회 기동 → k6 전체 실행)
- [x] **Step 2: 종료 순서 8단계** — 재기동 전 final metrics 저장 → 무결성 → 재기동·리컨실리에이션
  → 수집기 종료 → **마지막에** TRUNCATE
- [x] **Step 3: 계단별 집계** — `vu_level` 태그별로 **응답 가용성 · 1초 초과 건수 · 업무 성공률**.
  **`ramp` 태그는 제외**한다
- [x] **Step 4: 최초 실패 계단 식별** — 네 항목 중 하나라도 100%/0건이 아닌 **가장 낮은 계단**

> **이 결과를 통과·실패의 최종 근거로 사용하지 않는다.** 낮은 계단이 남긴 백로그는 높은 계단을
> 불리하게 만들지만, **캐시 warming은 유리하게** 작용할 수 있고 **오더북 성장은 체결 fan-out을
> 바꾼다.** **오염 방향은 사전에 확정할 수 없다** — Phase 1은 **탐색 전용**이다.

#### Step 5: 탐색 결과별 분기

| Phase 1 결과 | 다음 |
|---|---|
| **500에서 이미 실패** | **250 → (필요하면) 125**로 내려가 **최초 통과점**을 찾는다. 하한이 없다고 선언했으므로 아래로도 열려 있다 |
| 500 통과, 중간에서 실패 | 최고 통과와 최초 실패 사이를 Phase 2에서 좁힌다 |
| **4,000 전부 통과** | **기존 10,000 실패를 상한으로 사용**해 Phase 2에서 중간값(예: 7,000)부터 이분 |

**최종 해상도는 합산 250 VU로 사전 고정한다.** 그보다 좁히지 않는다(측정 비용 대비 의미 없음).

### Phase 3: 확증 — 방어 가능한 숫자 만들기

**세션 B는 "측정 1회"가 아니라 최소 3개의 독립 실행이다.** 각 실행마다 **초기화 → 부하 →
드레인 → 무결성·리컨실리에이션**까지 독립적으로 끝낸다(캐시 공정성 절차 + 종료 순서 8단계).

| # | 실행 | 목적 |
|---|---|---|
| 1 | **750 VU · 10분 hold** | 확증 1 |
| 2 | **750 VU · 10분 hold** | 확증 2 |
| 3 | **1,000 VU · 10분 hold** | 바로 위 후보의 **실패 재현**(경계가 실재함을 보인다) |

- [x] **실행 1·2** — 750을 깨끗한 DB에서 독립 실행, hold 10분. **2회 모두 전 항목 100%/0건**
      → **실행 1에서 실패**(업무 성공률 93.48%, 셰딩 36,989). 분기에 따라 **실행 2를 750으로
      반복하지 않고 500으로 내려가 2회 확증** — 500 2회 모두 전 항목 100%/0건 **통과**
- [x] **실행 3** — 1,000을 같은 방식으로 실행 → **수행하지 않음.** 목적이 "바로 위 후보의 실패로
      경계가 실재함을 보인다"인데, **500의 바로 위 후보 750의 실패가 실행 1에서 이미 재현**됐다
      (1,000은 32-A의 3분 hold에서도 이미 실패)

#### 판정 분기 (고정)

| 결과 | 판정 |
|---|---|
| **750 두 번 모두 통과 + 1,000 실패** | **현재 구성의 최고 검증 VU = 750.** `750 통과 / 1,000 실패`로 보고 |
| **750이 한 번이라도 실패** | **평균 내지 않고 탈락.** **500으로 내려가 다시 2회 확증** |
| **1,000이 통과** | **750을 최고라고 확정하지 않는다.** 경계가 위에 있다는 뜻이므로 **상향 탐색을 재개**한다(1,250 → …) |

> **성공 1회·실패 1회를 평균 내어 통과시키지 않는다.** 판정값은 100%/0건이고, 한 번의 실패는
> "그 VU에서 100%가 유지되지 않는다"는 증거다.

> **리컨실리에이션이 비정상적으로 길어져도 건너뛰지 않는다.** 32-A에서 체결 362,654건에 약 17.5분이
>걸렸고 10분 hold는 체결량이 더 크다. **시간 예산에 미리 넣고, 실제 소요 시간을 별도 운영 신호로
> 기록**한다(원인 미확정 진단 백로그 항목이다).
- [x] **증가하는 백로그가 없는지** 확인:
  - `settlement_outstanding_jobs`가 `2N`에 상시 붙지 않을 것
  - 정산 큐 길이가 시간에 따라 **단조 증가하지 않을 것**
  - 풀 `wait_count` 델타가 hold 구간에서 **증가 추세가 아닐 것**
  - 드레인 시간이 hold 길이에 비례해 늘어나지 않을 것
- [x] 10분 hold의 **전반 5분과 후반 5분을 나눠** 위 지표를 비교한다 — **후반이 나빠지면
  "지속 가능"이 아니다**(3분 hold로는 안 보이는 누적 효과)
      → **750: 셰딩 1,976 → 34,349(17.4배), `2N` 점유 26.5% → 99.3% — 실패.**
      **500: 셰딩 0 → 0, `2N` 점유 0.7% → 16.9% — 통과.** 다만 500도 worker busy
      44.9% → 72.9%, dispatch 0.47ms → 8.49ms로 **같은 상승 추세**를 보인다

## 한계 (문서에 반드시 남길 것)

- **유한 테스트다.** "영원히 100%"가 아니라 **측정 조건에서 실패 0건이었던 최고 검증 VU**다.
- **workload-specific**이다. 주문 혼합·취소 비율·think time이 달라지면 숫자도 달라진다.
- **Phase 1(계단식)은 오염된 관측**이다 — 낮은 계단의 백로그가 이어진다. 판정 근거는 Phase 3뿐이다.
- **run-to-run 분산**: 처리율 계열은 29·30번에서 재현이 확인됐으나(최대 편차 −0.9%),
  **지연 p95는 약 35% 분산**이 확인됐다. 그래서 판정을 **p95가 아니라 1초 초과 건수**로 잡았다.
- **VM 호스트 분산**은 분리하지 않는다.
