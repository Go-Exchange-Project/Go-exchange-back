  지배적이고 배치 파편화는 그 fence의 하류 결과**로 정정됐다(27번의 정산 큐 포화 재현 포함).
- **완료일**: 2026-07-29
- **성격**: **관측성-only.** 정산 스케줄링·배리어·재시도·폴백·배치 구성은 한 줄도 바꾸지 않았다.
- **근거**: [27번 재분석](../benchmarks/27-2026-07-28-settlement-binding-reanalysis.md)이 정산 경로를
  최초 바인딩 링크로 확정했지만, 그 안에서 **batch 파편화**와 **barrier wait** 중 무엇이 지배적인지는
  구분하지 못했다. [설계 스펙](../superpowers/specs/2026-07-28-settlement-observability-design.md)과
  [구현 계획](../superpowers/plans/2026-07-29-settlement-observability.md)(Task 1~5 전체 체크 완료)을
  그대로 따랐다.

## 왜 필요했나

27번은 정산 큐가 256(cap)으로 포화돼 있고 배치 평균이 2.82/32로 작다는 것까지는 확인했지만, 라이브
배치 경로의 실제 DB 지연·배리어 진입 빈도·배리어 대기 시간·job 디스패치 대기를 관측할 계측이 전혀
없었다. 종결 이벤트(전체의 31.9%)가 배치를 파편화하고 파티션 전체 배리어를 반복시킨다는 가설은
강하게 지지됐지만, **배리어 자체의 대기 비용**과 **파편화로 인한 트랜잭션 수 증가** 중 어느 쪽이
지배적인지 구분할 수 없어 다음 수정(주문별 fence / batch 재구성 / DB 최적화 / pool 튜닝) 중 어디를
겨냥해야 할지 확정할 수 없었다.

## 어떻게 했나

### 신규 메트릭 6종 (`internal/metrics/metrics.go`)

| 메트릭 | 타입 | 라벨 |
|---|---|---|
| `settlement_attempt_duration_seconds` | Histogram | `path=batch\|single` |
| `settlement_barriers_total` | Counter | `type=market_done\|cancel` |
| `settlement_barrier_wait_seconds` | Histogram | `type` |
| `settlement_barrier_inflight_batches` | Histogram | `type` |
| `settlement_job_dispatch_wait_seconds` | Histogram | (라벨 없음) |
| `settlement_job_execution_seconds` | Histogram | `result=success\|fallback\|failed`(이번 사이클은 `success`만 관측) |

고정 라벨 조합(`path`·`type`·`result`)은 `internal/metrics/metrics.go`에서 초기화 시 1회
`WithLabelValues`로 resolve해 패키지 변수(`SettlementAttemptBatch`, `SettlementBarrierCancel` 등)로
export했다 — hot path(`cmd/main.go`, `cmd/settlement_pipeline.go`)는 이 변수를 그대로 `.Observe()`/
`.Inc()`할 뿐, 이벤트마다 라벨 map을 조회하지 않는다.

**기존 `order_settlement_duration_seconds`는 관측 지점·의미·라벨을 전혀 바꾸지 않았다** —
`processTradeSettlement`의 재시도 루프 전체를 감싸는 기존 관측은 그대로 두고, 신규
`settlement_attempt_duration_seconds{path}`를 별도로 추가해 DB 호출 1회 단위를 관측한다.
과거 시계열의 해석이 깨지지 않는다.

### 관측 지점 3곳

1. **DB attempt** (`cmd/main.go`) — `settleTradeBatchWithFallback`의 `SettleTradeBatch` 호출 1회를
   `path="batch"`로, `processTradeSettlement`의 재시도 루프 **각 시도**(최초 호출 포함)를
   `path="single"`로 관측. 재시도 3회면 attempt 샘플 3개, 기존 `OrderSettlementDuration`은
   여전히 논리 1건.
2. **배리어** (`cmd/settlement_pipeline.go`, `runPartitionDispatcher`) — 종결 이벤트를 만나
   `pendingTerminal`을 설정하는 시점(배리어 진입)에 `barriers_total`을 증가시키고 그 순간의
   `inFlight`를 `barrier_inflight_batches`로 관측; in-flight가 0이 되어 `runTerminal`을 부르기
   직전(배리어 해제)에 `barrier_wait_seconds`를 관측한다. **in-flight가 이미 0이어도
   barriers_total은 증가**시켜 "배리어는 빈발하나 대기는 0"인 파편화 신호를 놓치지 않는다.
3. **job 타이밍** (`cmd/settlement_pipeline.go`) — `settlementJob`에 `dispatchAt time.Time`을
   추가해 dispatcher가 `readyJob`을 구성한(=송신을 시도하기 시작한) 시점을 기록하고,
   `runSettlementWorker`가 채널에서 job을 받은 시점에 `job_dispatch_wait_seconds`를 관측한다.
   worker 실행 시작부터 job 완료까지는 `job_execution_seconds{result="success"}`로 관측한다.

### `result` 라벨 제한 (의도된 축소)

`settleBatch`(=`settleTradeBatchWithFallback`)는 반환값이 없어 worker가 성공/폴백/실패를 구분할
수 없다. 이번 패치는 **`success`만 관측**하고, `fallback`/`failed` 구분은 결과를 worker로 되돌려줄
경로가 필요한 **별도 사이클**로 미룬다 — 이번 사이클에서 반환값 배선까지 하면 관측성-only 원칙을
넘어서는 동작 변경이 되기 때문이다. `settlement_job_execution_seconds{result="fallback"}`/
`{result="failed"}`는 메트릭 자체는 선언돼 있지만 이번 패치에서는 항상 0이다.

## 성능 회귀 확인

이번 패치가 건드린 hot path(`cmd/settlement_pipeline.go`, `cmd/main.go`의 정산 함수)에는 이 저장소에
전용 Go 벤치마크가 없다. 유일한 기존 벤치마크(`internal/matching/engine_bench_test.go`)는 매칭
엔진(`internal/matching`)만 실행하며 정산 파이프라인을 전혀 호출하지 않는다 —
`git diff --stat c2688cc..HEAD -- internal/matching/`가 빈 결과를 반환해 이 패키지가 이번 커밋들에서
전혀 수정되지 않았음을 확인했다. 따라서 이 벤치마크의 패치 전/후 수치는 **정의상 동일**하다(같은
코드를 실행). 참고용으로 기록:

정산 hot path의 회귀 여부는 대신 **코드 검토**로 확인했다(스펙의 "성능 회귀 조건"과 동일 기준):
- 라벨 조합은 전부 `internal/metrics/metrics.go`에서 패키지 초기화 시 1회 `WithLabelValues`로

  배리어는 진입·해제 각 1회, job은 dispatch/exec 각 1회 — trade 건별로는 기록하지 않는다(배치 단위).

### 판정표 적용 (이번 로컬 데이터 기준)

| 지표 | 값 |
|---|---|
| 평균 배치 크기 | 517 trades / 374 batches = **1.38** |
| `attempt_duration{batch}` 평균 | 4.572s / 374 = **12.2ms** |
| `job_execution{success}` 평균 | 4.595s / 374 = **12.3ms**(attempt 평균과 거의 동일 — 비-DB 오버헤드 미미) |
| `job_dispatch_wait` 평균 | 0.0022s / 374 = **5.9µs**(무시할 수준) |
| `barrier_wait{cancel}` 평균 | 0.0127s / 92 = **0.14ms** |
| `barrier_wait{market_done}` 평균 | 2.358s / 203 = **11.6ms** |
| `barrier_inflight{market_done}` 평균 | 198 / 203 = **0.98**(배리어 진입 시 거의 항상 in-flight 배치 1개 이하) |

`job_dispatch_wait`가 무시할 수준이라 **pool·스케줄링 한계는 배제**된다. `barrier_wait`는
`market_done`에서 attempt 1건과 같은 자릿수(11.6ms)로, **누적 대기가 쌓이는 모습이 아니라 배리어당
in-flight 배치 1개(평균 0.98)를 기다리는 정도** — 파티션 전체 fence가 누적 지연을 만드는 신호는
아니다. 반면 **평균 배치 크기가 1.38로 최소치에 근접**했고 attempt 샘플 수가 배치 수와 1:1(재시도
없음)이면서도 배치당 trade가 거의 늘지 않는다 — **batch 파편화가 지배적**이라는 판정표 2번째 행에
해당한다: *"barrier_wait 작은데 attempt_duration 샘플 수 많음(=배치가 잘게 끊겨 트랜잭션 수가
많음) → batch 구성 변경."*

이 결과는 27번의 가설(종결 이벤트로 인한 배치 파편화)과 **방향이 일치**한다. 다만 이번 로컬
통제 부하는 **피크 30 VU** 규모로, 27번이 관측한 GCP 스케일(정산 워커 큐 256 포화, 135 trades/s)의
**동시성 압력을 재현하지 않는다** — 이 판정은 계측이 올바르게 신호를 분리해낸다는 것을 증명하는
것이지, 27번의 GCP 결론을 이 로컬 규모로 재확정하는 것은 아니다. GCP 스케일에서 같은 4종 계측으로
재측정하는 것은 27번 문서가 이미 명시한 별도 후속 사이클이다.
