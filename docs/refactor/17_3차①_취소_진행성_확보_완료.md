# 17. 3차 리팩토링 ① 취소 진행성 확보(P2 완화) — 완료

- **완료일**: 2026-07-26
- **설계 문서**: [3차 ① 하류 포화 시 신규 주문 억제 설계](../superpowers/specs/2026-07-26-cancel-progress-under-backpressure-design.md)
- **구현 계획**: [3차 ① 취소 진행성 확보 구현 계획](../superpowers/plans/2026-07-26-cancel-progress-under-backpressure.md)

## 왜 필요했나

23번 벤치마크(⑤)가 실측한 취소 48.7% 실패의 지배 원인은 P2였다 — 엔진 goroutine이
`emitTrade`의 블로킹 `ExecutionCh` 송신에서 멈추면, 2차③(취소 우선 select)의
루프 상단 우선순위 자체가 무의미해진다(루프가 select로 돌아오지 못하니 우선순위를
쓸 기회가 없다). ③(SLI 3분할)이 이 문제를 세 지표로 정확히 잴 토대를 먼저
깔았고, ①이 그 위에서 P2를 겨냥한 첫 완화책이다.

## 어떻게 해결했나

`internal/matching/engine.go`에 하류(`ExecutionCh`) 인지 게이트를 추가했다 —
별도 goroutine·히스테리시스·wake 신호 없이, 기존 루프의 순서를 그대로 유지한다.

1. **`emitBackpressured()` 헬퍼**: `ExecutionCh` 점유가 용량의 75%(`engineEmitHighWatermarkRatio`)
   이상이면 `true`. `nil` 수신자·`nil` 채널·`cap == 0` 채널 모두 안전하게 `false`
   (nil 수신자는 `||` 단락 평가로 필드 역참조 전에 걸러지고, `cap == 0` 가드가
   없으면 버퍼 없는 채널에서 게이트가 영구 켜짐 상태로 고착되는 걸 막는다).
2. **`Start()` 루프의 신규 주문 억제**: 하류가 밀리면 두 번째 select에서
   `me.OrderCh`를 지역 변수 `orderCh`에 `nil`로 대입 — 취소·ticker·stop은
   그대로 흐르고, 신규 주문만 그 반복에서 안 꺼내진다. `me.OrderCh` 필드
   자체는 손대지 않아 `SubmitOrder`/`TrySubmitOrder` 송신자는 영향받지 않는다.
   2차③의 1단계(취소 논블로킹 우선 드레인)는 이 게이트보다 먼저 실행되므로
   완전히 무관하게 유지된다.
3. **`IsIntakeAdmissible`에 하류 조건 AND**: 기존 `OrderCh` 워터마크 조건에
   `!emitBackpressured()`를 추가 — 게이트가 꺼져 있으면(`emitBackpressured()`
   false) 기존 동작과 완전히 동일(`X && !false ≡ X`).

`0.75`는 정합성 경계가 아니라 측정용 초기 운영값이라는 성격을 상수 주석에
영문 그대로 명시했다(이전 리뷰 라운드에서 확정된 문구, 리라이트하지 않음).
`emitTrade`·매칭 로직(`matchSell`/`matchBuy`)·`drainPendingWork`·shutdown
도미노·`internal/matching/sharded.go`는 전부 무변경 — `ShardedEngine`은 샤드별
`MatchingEngine`에 위임하므로 게이트가 샤드마다 자동 적용된다(각 샤드의
`emitTrade`가 자기 샤드의 `ExecutionCh`를 막으므로, 게이트가 측정하는 채널이
정확히 블로킹되는 채널과 같다).

### 게이트 해제 지연 (의도된 폴링)

`orderCh = nil`인 동안 하류가 W 아래로 드레인돼도 엔진 select를 깨우는 신호가
없다 — 다음 snapshot ticker(테스트 2ms, 운영 ~100ms)에 재평가된다. 즉 회복
후 신규 주문 소비 재개는 최대 약 100ms 지연될 수 있다. 초기 완화안에서는 이를
허용한다(취소는 그동안에도 계속 처리됨) — 실측상 문제가 될 때만 명시적 wake
신호를 검토한다.

## 결과

4개 TDD 테스트, 전부 GREEN:

- **(A) 게이트가 신규 주문을 억제**: `ExecutionCh`를 W까지 채우고 체결을
  만들지 않는 non-crossing limit order를 `OrderCh`에 넣은 뒤, 여러 ticker
  주기 동안 주문이 `OrderCh`에 남아있음을 확인 → `ExecutionCh`를 W 아래로
  드레인 후 `assert.Eventually`(한 ticker 이상)로 처리 재개 확인. **게이트
  없는 코드에서 실제로 RED임을 확인**(두 절반이 서로를 제약해 우연히 통과할
  수 없는 구조 — 리뷰가 독립적으로 이를 검증).
- **(B) 취소 진행 확인**: 게이트가 켜진 상태에서 `CancelOrder`가 넉넉한
  데드라인(500ms, 실제 1초 타임아웃보다 훨씬 짧음) 내 성공함과 동시에
  `OrderCh`가 그동안 유지됐음을 단언(취소 성공만이 아니라 억제도 함께 증명).
  **이 테스트는 P2(엔진이 실제로 `ExecutionCh` 만석에 블록된 상태)를 재현하지
  않는다** — `ExecutionCh`를 75%(W)까지만 채워 25% 헤드룸이 있으므로 취소
  emit은 게이트 유무와 무관하게 막히지 않는다. 리뷰에서 지적받아 테스트
  메시지를 "게이트 on 상태에서도 취소가 계속 처리됨"으로 정정했다(P2 재현
  주장 제거) — 테스트 자체는 유효한 회귀 가드(미래에 취소가 게이트에 걸리는
  변경이 생기면 잡아낸다)이지만, P2 완화 효과의 증거는 아니다.
- **(C) `IsIntakeAdmissible` 하류 조건**: `ExecutionCh ≥ W`면 `OrderCh`가
  비어 있어도 `false`.
- **(D) `emitBackpressured` 경계**: `nil` 수신자·빈 채널·`cap == 0` 채널
  모두 `false`.

기존 엔진·취소·샤딩·2차③ 테스트 무수정 그린 — 특히 `TestEngineProcessesCancelsBeforeNewOrders`
(2차③)는 `ExecutionCh`를 10개만 채우므로(cap 1024) 게이트가 켜지지 않아
완전히 무관함을 확인했다. `go build`/`go vet`/전체 스위트(SKIP 0)/`-race`
(matching·service·cmd) 전부 그린.

리뷰(opus, 매칭 엔진 코어 루프 리스크 고려): 변경 범위가 `engine.go`에만
국한됐는지, 2단계 우선순위 select의 1단계가 무관하게 유지됐는지, `0.75`
주석이 그대로인지, nil/cap-zero 안전성, 별도 goroutine·히스테리시스 부재,
`IsIntakeAdmissible`의 게이트-off 무회귀, `ShardedEngine` 무변경(위임 모델이
실제로 같은 채널을 측정함을 추적 확인) — 9개 구속조건 모두 diff에서 직접
추적해 확인. Important 1건(테스트 B의 실패 메시지 과잉 주장) 발견 후 수정,
Critical 0건.

## 주장의 범위 — 정직하게

**이건 일반적 취소 진행 보장이 아니라 완화책이다.** 핵심 반례: 신규 주문
한 건이 무제한 체결을 만들 수 있다 — 매칭 루프는 상대 주문을 만날 때마다
동기식으로 `ExecutionCh`에 emit하고 체결 수 상한이 없다. `ExecutionCh`가
767일 때 신규 주문 하나가 300개 maker와 체결되면, 257번째 emit에서 채널이
꽉 차 엔진이 다시 멈춘다 — 루프 상단의 게이트로 돌아오기도 전에.

- **비보장**: 임의 fan-out 주문(한 주문이 대량 체결) + 하류 완전 정지
  (드레인 0).
- **정산 천장은 안 높인다**(그건 3차②) — 게이트가 DB 홀드 전에 요청을
  거절하므로 접수량·응답 지연·안정 처리량은 달라질 수 있으나, 최대 정산
  용량을 늘리는 설계가 아니다.
- **shutdown 상호작용**: `drainPendingWork`는 게이트를 무시한다(의도적 —
  게이트는 메인 루프에만, 드레인은 별도 경로). 게이트가 켜진 상태로 shutdown이
  오면 `OrderCh`가 깊어진 채 헤드룸 256만 남을 수 있어 이론상 셧다운을
  더 오래 걸리게 만들 수 있다(기존 `cmd/main.go`의 30초 drain deadline이
  이를 감싸므로 무한 대기는 아님) — 코드 변경은 하지 않았으나 이 가능성은
  기록해둔다.
- **취소 인프라 실패 0 실증은 재측정이 결정한다** — ⑤(23번) 재실행 또는
  후속 벤치마크에서 3차③의 `sli_cancel_success`로 판정한다. **이 문서는
  수치를 주장하지 않는다.**
