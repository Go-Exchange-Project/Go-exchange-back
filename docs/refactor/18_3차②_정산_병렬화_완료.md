## 왜 필요했나

24번 진단이 5회의 독립된 부하 재현에서 예외 없이 동일한 패턴을 확정했다 —
`settlement_worker_queue_length{worker="8"}`가 항상 256(cap)까지 포화되고
나머지 9개 워커는 항상 0. BTC 단일 심볼의 정산이 심볼 해시로 항상 같은 워커
1개에 몰려 DB 왕복마다 순차 직렬화되는 것이 처리량 천장이었다(DB·backend
CPU 모두 유휴에 가까워 자원 경쟁이 아니라 순수 직렬화임도 함께 확인됨).

## 어떻게 해결했나

**정산 DB 작업은 병렬로, 외부로 나가는 브로드캐스트는 순서대로.** 정산
도메인 로직(`settleTradeBatchWithFallback`·`processSingleOutboxEvent`·
`SettlementService.SettleTradeBatch`)은 시그니처·본문 전부 무변경 — 이미
파라미터로 있던 `broadcast` 자리에 "수집 closure"를 주입해 방출만 지연시키는
것이 설계의 핵심이다.

1. **`GOEXCHANGE_SETTLEMENT_CONCURRENCY`(신규, 기본 4)** — 전역 동시 정산
   트랜잭션 수. 기존 `GOEXCHANGE_SETTLEMENT_WORKERS`(파티션 수 P, 순서 보존
   단위)의 의미는 전혀 바꾸지 않고 별도 축으로 분리했다. DB 풀(기본 25)을
   주문 홀드·아웃박스·리컨실리에이션과 공유하므로 보수적 기본값에서
   시작한다.
2. **파티션당 dispatcher 1개 + 전역 worker pool N개**(`cmd/settlement_pipeline.go`):
   - dispatcher는 **jobs 디스패치·completion 수신·입력 수집을 하나의 select로
     multiplex**한다 — 분리 블로킹하면 worker가 가득 찬 completion 채널
     송신에서 막힐 때 dispatcher가 jobs를 못 비우는 교착이 가능하다.
   - **`completions` 채널 용량 = concurrency**(최대 in-flight) — 이 불변식이
     worker의 `job.done <-` 송신이 절대 영구 블로킹하지 않음을 보장한다.
   - 완료가 뒤섞여도 **`nextBroadcastSeq`부터 연속으로만** 방출(pending
     map) — 순서를 흩뜨리면 프런트가 수신 순서로 최근 체결 목록에 삽입하므로
     (`Index.tsx:294`) 사용자 가시 회귀가 된다.
   - **종결 이벤트(비-trade) 배리어**: 종결 이벤트를 만나면 새 배치를
     dispatch하지 않고 completion만 수신(입력·jobs 케이스 nil 채널 비활성화)
     — in-flight가 단조 감소해 유한 시간에 0에 도달한 뒤에야 종결 이벤트를
     처리한다. 기아 없음.
3. **`main()` 배선**: 기존 파티션별 인라인 워커 루프를 위 dispatcher+pool로
   교체. 종료 순서는 **`settlementWg.Wait()`(모든 dispatcher 반환) →
   `close(settlementJobs)` → `settlementWorkerWg.Wait()`(pool 전부 반환) →
   `close(settlementDrained)`** — dispatcher가 다 반환한 뒤에만 job 채널을
   닫아 send-on-closed를 방지한다.

## 정합성 검증 — A′ 결정과 실측된 오차

설계 문서가 실측으로 확인한 것: 잔고·수량은 덧셈뿐이라 순서 무관이지만,
**`AvgBuyPrice`는 매 체결마다 나눗셈(`(avg*qty + cost) / newQty`,
`shopspring/decimal` `DivisionPrecision=16`)을 거치므로 배치 완료 순서에
따라 유한 정밀도 마지막 자리가 달라질 수 있다.** 이 사이클은 "항상 1e-16"이라
단정하지 않고 실제로 측정했다:

- **순열 기반 오차 상한 측정**(`internal/service/avg_buy_price_permutation_test.go`,
  DB 불필요): 4건 체결의 5개 순열에 대해 러닝 가중평균 최대 오차를 측정한
  결과 **관측된 최대 오차 = `0.0000000000000001`(1e-16)**, 허용치
  `0.000001`(1e-6) 이내.
- **교차 배치 등가성 통합 테스트**(`internal/service/settlement_batch_concurrency_integration_test.go`):
  같은 지갑이 서로 다른 두 배치에서 매수 체결을 받는 시나리오를 (a) 고정
  순서(batch1→batch2), (b) **결정론적 역순 고정 순서**(batch2→batch1), (c)
  실제 goroutine 2개 동시 실행 세 가지로 처리해 비교. 정순 결과에는 **절대
  기대값**을 직접 검산해 단언했다(`Quantity=0.94`,
  `AvgBuyPrice=50006388.3558787234042553`) — 상대 비교만으로는 세 경로가
  똑같이 틀려도 통과할 수 있다는 리뷰 지적을 반영해, 역순 픽스처가 매 실행
  결정론적으로 오차를 관통시키도록 보강했다(반복 실행에서 "동시" 픽스처만으로는
  40%가 우연히 정순과 같은 순서로 커밋돼 아무것도 검증하지 못하는 경우를
  실제로 관측했다 — 이게 역순 픽스처를 추가한 근거다).

**반드시 동일해야 하는 것**(전부 `Equal()`): 지갑 `Available/Locked/KRW/
Quantity`, 주문 `FilledAmount`·상태, 원장 행 개수와 유저별 delta 합계,
`failed_settlements`/`failed_market_completions` 0건.
**동일 단언하지 않는 것**: 원장 행별 `AvailableBalanceAfter`/`LockedBalanceAfter`
(커밋 순서 의존, 이유를 코드 주석으로 명시), `AvgBuyPrice`의 유한 정밀도
마지막 자리(tolerance `0.000001`로 비교).

`AvgBuyPrice`는 표시·미실현 손익용 파생 상태이며 주문 승인·홀드·체결 금액·
출금 가능 잔액·원장 총량·리컨실리에이션 판정 어디에도 쓰이지 않는다 —
`reconciliation_worker.go`는 `avg_buy_price`를 검사하지 않는다.

## 주장의 범위 — 정직하게

- **처리량 수치는 이 문서에서 주장하지 않는다.** 이번 사이클의 산출물은
  "정산 병렬화가 정합성을 깨지 않는다"는 실증이지 처리량 개선 실증이 아니다.
  **실증은 24번과 같은 진단 하니스로 `GOEXCHANGE_SETTLEMENT_CONCURRENCY`
  1/2/4/8 스윕**을 통해 `settlement_worker_queue_length` 포화 해소 여부와
  실제 처리율 변화를 별도로 측정해야 한다.
  **→ 실증 완료**: [25번 재측정](../benchmarks/25-2026-07-27-settlement-parallelization-remeasurement.md).
  N=2·N=4에서 24번 부하 기준 바인딩 완전 해소(셰딩 0%, 정합성 위반 없음)를
  확인했으나, N=8에서는 데드락 재시도(신규 지갑 생성 경합)로 셰딩이 재등장해
  **기본값 4 유지를 권장**한다 — N에 비례하는 스케일링은 아니다.
- **N=1이면 기존 동작과 동등**하다는 것은 코드 추론으로 확인했다
  (concurrency=1일 때 dispatcher는 파티션당 in-flight 1을 유지하며 "수집 →
  정산 → 방출 → 다음"의 기존 순서를 그대로 재현) — 별도의 실측 벤치마크로
  재확인하지는 않았다.
- **AvgBuyPrice 오차 상한 `1e-16`은 이번에 쓰인 특정 픽스처(4건 체결,
  특정 가격·수량)에서 관측된 값**이지 수학적으로 증명된 절대 상한이 아니다.
  `0.000001`(1e-6)이라는 tolerance는 이 관측값보다 10,000배 넉넉한 값으로
  잡았다.
- **동일 주문 경합**(같은 주문의 부분 체결이 두 배치에 걸리는 경우)은 행
  락으로 안전하게 직렬화되지만, 단일 심볼 집중 부하에서는 자주 발생할 수
  있어 실효 병렬도가 이론값(N)보다 낮을 수 있다 — 이 역시 24번 재실행이
  실측으로 드러낼 부분이다.
