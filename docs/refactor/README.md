# 리팩토링 로드맵

2026-07-10 아키텍처 전수 리뷰(Fable5)에서 나온 개선 항목들의 진행 현황판입니다.
목표: **더 많은 사람이, 더 빠르게, 100% 정확도로 거래**할 수 있는 거래소.

## 운영 규칙

- 항목을 완료하면 아래 표의 상태를 ✅로 바꾸고, `N_항목이름_완료.md` 문서를
  이 디렉토리에 추가한다(N은 작업 완료 순서).
- 완료 문서에는 **왜 문제였는지 / 어떻게 해결했는지 / 결과가 어땠는지**를 적는다.
  상세 설계·검증 기록은 `docs/superpowers/specs/`의 해당 설계 문서에 있으므로
  완료 문서는 요약 + 링크로 유지한다.
- 우선순위 원칙: **정합성 구멍 → 정합성의 증명/보험 → 내구성 → 확장성** 순.
  병목이 아닌 곳을 먼저 최적화하지 않는다(16번 벤치마크의 교훈).

## 2차 리팩토링 — 가용성 100% (2026-07-18 착수)

1차(1~10번)로 **정합성**은 실전 급등락에서 위반 0으로 실증됐다([22번 2부](../benchmarks/22-2026-07-18-outbox-ab-and-spike.md)).
그런데 같은 22번이 **가용성 갭**을 드러냈다: 스파이크 시 취소 43.9% 실패(CancelCh
타임아웃)와 주문 접수 지연 초 단위(엔진 정지의 HTTP 역류). 둘 다 정합성이 아니라
**가용성** 문제다 — 돈이 오가는 서비스에서 가용성도 정합성과 같은 급으로 다뤄야 한다.

**목표(정직한 정의):** 동시 **~5,000 제출자(≈3,000건/s)** 까지 **① 즉시 접수(한 자릿수
ms p95) ② 취소 무실패 ③ 정합성 위반 0**을 급등 스파이크 주입으로 실증한다. 목표 초과
부하는 **매달림 없이 빠른 거절(503+재시도)** — "완료 또는 빠른 명확한 거절, 몇 초 매달림
0"이 하드 보장이다. 고정 하드웨어(스케일업 없음) 유지. 배칭으로 천장이 목표까지 닿는지
측정하고, 벽이면 인메모리 잔고로 승격(측정 기반 에스컬레이션).

> 근본 원인은 하나다: **DB CPU 포화 → ExecutionCh 만석 → 엔진 정지 → OrderCh/CancelCh
> 역류.** 취소 500·주문 14초·처리량 정체가 전부 이 한 뿌리의 세 증상이다.

## 3차 리팩토링 — 처리량 천장 + 취소 P2 (23번 후속)

> 23번이 실측한 새 그림: **DB는 더 이상 병목이 아니다(idle 75~86%)** — ②가 DB 왕복을
> 실제로 줄인 결과. 병목이 **엔진 자체 처리 + `ExecutionCh` 다운스트림(정산/아웃박스)
> 드레인**으로 옮겨갔다. 단일 심볼 BTC는 `main.go:426`의 심볼 해시로 **정산 워커 1개**에
> 몰려 직렬화되고, `emitTrade`의 블로킹 `ExecutionCh` 송신이 엔진을 멈춰(P2) 취소를 굶긴다.
> 규율: **안 재고 고치지 않는다** — 처리량 수정은 pprof 진단이 선행한다.

## 4차 리팩토링 — 안전한 처리량 증대와 매칭 진행성

> 26번이 남긴 두 숙제. **두 축은 독립적으로 판정한다** — 축 1이 성공해도 축 2의 무한 점유 반례는
> 남고, 축 2를 구현해도 하류 처리율이 그대로면 업무 성공률은 크게 오르지 않는다. 섞지 않는다.

**1. 안전한 지속 처리율 증대** (업무 성공률 개선)
- 하류 **단계별 처리율**을 측정한 뒤 **최초 바인딩 링크 하나만** 표적 수정 → 재측정 → 새 바인딩
  링크 재판정. **워터마크 조정은 처리율 개선 이후 마지막**에만.
- **원칙: 업무 성공률을 올리려고 게이트부터 느슨하게 하지 않는다**(그 길은 23번 A의 p95 24초 매달림).
- 26번 관측의 범위: **현재 26번 부하·구성에서는** 엔진이 하류보다 빠르게 이벤트를 생산할 수 있으므로
  최초 개선 대상은 하류다. **하류 처리율을 올린 뒤에는 바인딩 링크를 다시 판정해야 한다**(엔진이
  영원히 병목이 아니라는 뜻이 아니다).

**2. 매칭 quantum** (최악 fan-out에서의 진행성)
- 심볼별 **single-writer와 가격·시간 우선순위를 유지하면서**, 한 주문이 이벤트 루프를 무한 점유하지
  못하게 한다(한 번의 점유 ≤ K건 또는 T시간).
- 판정 기준은 TPS가 아니라: **임의의 대형 fan-out에서도 취소 처리 기회가 유한 시간 안에 주어지고,
  기존 체결 결과와 외부 이벤트 순서가 바뀌지 않는다.**
- 설계 전 닫아야 할 계약(별도 브레인스토밍): 중단된 주문보다 신규 주문이 앞설 수 있는가 / 중단된
  주문을 취소할 수 있는가 / maker가 중간에 취소되면 재개 커서는 / 부분 실행 중 우선순위 보존 /
  Done·Cancel·Trade 방출 순서 / 재개 상태에서 프로세스가 죽으면 복구.

**공통 회귀 게이트**(매 단계 충족):
- 응답 가용성 유지
- **취소 인프라 실패율 0%**(정상 경쟁인 404·409는 제외)
- 정합성 위반 및 `settlement_batch_fallbacks_total` 0
- 회복 성능 악화 없음

**현재 단계**: ✅ **A+C 완료 + 29번 GCP 재측정으로 최종 판정 완료** →
[29번 GCP 스케일 최종 판정](../benchmarks/29-2026-07-30-per-order-fence-gcp-remeasurement.md).
**파티션 전체 fence는 제거됐고 바인딩 링크가 "fence 대기"에서 "정산 워커·DB 처리 용량(N=4)"으로
이동했다** — worker busy 13.1%→99.95%, 정산 처리율 ≈109→≈372 trades/s, 업무 성공률
10.82%(26번)→22.70%. 정합성·무결성 전항목 통과, 가용성·취소 하드 보장 유지.
**단, 28번이 "배리어가 배치 누적을 가로막는다"고 설명한 평균 배치 2.8은 fence 제거 후에도 2.78로
그대로여서 그 인과 주장은 반증됐다.** 대신 **terminal 경계가 batch run length를 제한한다는 새 가설**이
수치상 강하게 지지된다(`collectTradeBatch`가 비-trade 이벤트에서 배치를 끊고, terminal이 전체 이벤트의
31.9%다 — 독립 혼합 가정 아래 근사 `1/0.319≈3.13` vs 관측 2.78~2.83). **가설이지 확정된 인과가 아니며,
실제 연속 trade run-length 분포를 다음 측정에서 직접 계측해 확인해야 한다.**

**남은 것은 축 2뿐이 아니다.** 다음 두 갈래를 **병렬이 아니라 독립 순서로** 관리한다 —
서로 판정을 섞지 않는다:

1. **축 1 후속 — terminal 경계 배치 파편화 진단**(진단 선행: run-length 분포, job 종류별 실행 시간
   분리, terminal의 DB transaction 비중). **`N=4 → 8` 통제 비교**도 이 갈래이며, 29번 사후 분석에서
   **DB 풀 대기가 초기 램프에 집중되고 정상 구간 `in_use`는 max 8 / p95 6(상한 25)**로 확인돼
   시험할 여지가 있다 — 단 **서버·DB CPU를 함께 재야** 하고 N=8의 안전성·효과는 미실증이다.
2. **축 2 — 매칭 quantum**(최악 fan-out에서의 진행성, 계약 6개 선결)

**어느 쪽을 먼저 할지는 29번의 업무 성공률 개선폭(10.82%→22.70%)까지 포함해 결정한다.**

- 28번(GCP 스케일 관측성 재측정)이 27번의 정산 큐 포화(`worker="8"`=256 cap)를 정확히 재현하고
  **파티션 전체 fence가 지배적**이라고 판정(hold 구간 `market_done` 배리어 wait duty 52.3%, 배리어
  진입 시 in-flight 항상 1)한 뒤, 그 fence를 주문별로 좁히는 A(런타임 fence)를 설계하려던 중
  **더 근본적인 정합성 구멍**을 발견했다: `SettlementRetryWorker.retryFailedCompletions`가 그
  주문의 미해결 failed settlement를 확인하지 않아 **미정산 trade 위에서 시장가 완료가 실행**되고
  잔여 홀드를 잘못 반환할 수 있었다. A를 먼저 넣어도 실패 순간엔 이 순서 위반이 그대로 성립하므로,
  **B를 먼저 닫아 "복구 경로는 순서를 지킨다"는 전제를 확보**했다(성능과 무관한 독립 버그 수정).
- B: `HasOpenFailureForOrder`(DB EXISTS)를 repository→service→워커 네 계층에 통과시켜, 같은 주문을
  참조하는 `OPEN` failed settlement가 있으면 시장가 완료 terminal을 durable defer한다. dependency
  store가 nil이거나 조회 오류면 phase 단위 fail-closed(이번 사이클 completion 전체 중단). 차단은
  `settlement_completion_blocked_total` 카운터로만 관측(로그 없음).
- **A+C 완료**: dispatcher의 파티션 전체 배리어를 `dependencyTracker`(주문ID→미retire 배치 수) 기반
  주문 단위 fence로 축소 — 28번이 실측한 "무관한 주문의 배치까지 막히는" 문제를 직접 해소했다.
  취소 terminal에도 시장가 완료와 동형의 durable defer 계약(`FailedOrderCancellation`,
  `RecordFailure`/`EnsureDeferred` 구분, `retry_count=0` 시작)을 갖췄다. 배리어 지표
  (`settlement_barriers_total` 등)를 제거하고 `settlement_terminal_wait_seconds`/
  `settlement_outstanding_jobs`/`settlement_quarantined_orders`/
  `settlement_dependency_record_failed_total`로 교체. 자세한 내용과 대화 중 정정된 사항은
  [22번 완료 문서](22_4차_축1_per-order_fence_완료.md) 참고.
- **29번 GCP 실측 완료**(측정 기준 SHA `82b4d7f`,
  [runbook](../superpowers/plans/2026-07-30-per-order-fence-gcp-remeasurement.md) →
  [결과](../benchmarks/29-2026-07-30-per-order-fence-gcp-remeasurement.md)): 폐기한 배리어 지표가
  실제로 사라지고 신규 5종이 정상 동작함을 확인, 계측 내부 무결성 9항목이 오차 0으로 일치했다.
  주의: runbook의 주 가설 기준("terminal wait p50 감소")은 **28번 barrier wait과 측정 대상이 달라
  직접 비교가 성립하지 않는다** — fence 제거 판정은 처리량 지표를 근거로 했다.

## 리뷰에서 나왔지만 채택하지 않은 것

- **MSA 전환**: 매칭 엔진의 본질이 심볼당 단일 스레드 직렬화라 분산해도 병렬화되지
  않음. 모듈러 모놀리스 유지. 유일한 분리 후보는 WS market-data fanout(B-1 이후 재판단).
- **Kafka**: 단일 브로커는 Postgres COMMIT 대비 추가 내구성이 0인데 dual-write 문제를
  새로 만듦. A-3의 transactional outbox가 정석 관문(추후 CDC로 전환 경로 열림).
- **Redis**: 단일 프로세스에선 `atomic.Value`(인프로세스)가 항상 우월. WS를 다중
  인스턴스로 분리하는 시점에 pub/sub으로 첫 도입.
