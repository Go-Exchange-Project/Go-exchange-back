## 2차 리팩토링 — 가용성 100% (2026-07-18 착수)

1차(1~10번)로 **정합성**은 실전 급등락에서 위반 0으로 실증됐다([22번 2부](../benchmarks/22-2026-07-18-outbox-ab-and-spike.md)).
그런데 같은 22번이 **가용성 갭**을 드러냈다: 스파이크 시 취소 43.9% 실패(CancelCh
타임아웃)와 주문 접수 지연 초 단위(엔진 정지의 HTTP 역류). 둘 다 정합성이 아니라
**가용성** 문제다 — 돈이 오가는 서비스에서 가용성도 정합성과 같은 급으로 다뤄야 한다.

**목표(정직한 정의):** 동시 **~5,000 제출자(≈3,000건/s)** 까지 **① 즉시 접수(한 자릿수
ms p95) ② 취소 무실패 ③ 정합성 위반 0**을 급등 스파이크 주입으로 실증한다. 목표 초과
부하는 **매달림 없이 빠른 거절(503+재시도)** — "완료 또는 빠른 명확한 거절, 몇 초 매달림
0"이 하드 보장이다. 고정 하드웨어(스케일업 없음) 유지. 배칭으로 천장이 목표까지 닿는지
측정하고, 벽이면 인메모리 잔고로 승격(측정 기반 에스컬레이션).

> 근본 원인은 하나다: **DB CPU 포화 → ExecutionCh 만석 → 엔진 정지 → OrderCh/CancelCh
> 역류.** 취소 500·주문 14초·처리량 정체가 전부 이 한 뿌리의 세 증상이다.

## 3차 리팩토링 — 처리량 천장 + 취소 P2 (23번 후속)

> 23번이 실측한 새 그림: **DB는 더 이상 병목이 아니다(idle 75~86%)** — ②가 DB 왕복을
> 실제로 줄인 결과. 병목이 **엔진 자체 처리 + `ExecutionCh` 다운스트림(정산/아웃박스)
> 드레인**으로 옮겨갔다. 단일 심볼 BTC는 `main.go:426`의 심볼 해시로 **정산 워커 1개**에
> 몰려 직렬화되고, `emitTrade`의 블로킹 `ExecutionCh` 송신이 엔진을 멈춰(P2) 취소를 굶긴다.
> 규율: **안 재고 고치지 않는다** — 처리량 수정은 pprof 진단이 선행한다.

## 4차 리팩토링 — 안전한 처리량 증대와 매칭 진행성

> 26번이 남긴 두 숙제. **두 축은 독립적으로 판정한다** — 축 1이 성공해도 축 2의 무한 점유 반례는
> 남고, 축 2를 구현해도 하류 처리율이 그대로면 업무 성공률은 크게 오르지 않는다. 섞지 않는다.

**1. 안전한 지속 처리율 증대** (업무 성공률 개선)
- 하류 **단계별 처리율**을 측정한 뒤 **최초 바인딩 링크 하나만** 표적 수정 → 재측정 → 새 바인딩
  링크 재판정. **워터마크 조정은 처리율 개선 이후 마지막**에만.
- **원칙: 업무 성공률을 올리려고 게이트부터 느슨하게 하지 않는다**(그 길은 23번 A의 p95 24초 매달림).
- 26번 관측의 범위: **현재 26번 부하·구성에서는** 엔진이 하류보다 빠르게 이벤트를 생산할 수 있으므로
  최초 개선 대상은 하류다. **하류 처리율을 올린 뒤에는 바인딩 링크를 다시 판정해야 한다**(엔진이
  영원히 병목이 아니라는 뜻이 아니다).

**2. 매칭 quantum** (최악 fan-out에서의 진행성)
- 심볼별 **single-writer와 가격·시간 우선순위를 유지하면서**, 한 주문이 이벤트 루프를 무한 점유하지
  못하게 한다(한 번의 점유 ≤ K건 또는 T시간).
- 판정 기준은 TPS가 아니라: **임의의 대형 fan-out에서도 취소 처리 기회가 유한 시간 안에 주어지고,
  기존 체결 결과와 외부 이벤트 순서가 바뀌지 않는다.**
- 설계 전 닫아야 할 계약(별도 브레인스토밍): 중단된 주문보다 신규 주문이 앞설 수 있는가 / 중단된
  주문을 취소할 수 있는가 / maker가 중간에 취소되면 재개 커서는 / 부분 실행 중 우선순위 보존 /
  Done·Cancel·Trade 방출 순서 / 재개 상태에서 프로세스가 죽으면 복구.

**공통 회귀 게이트**(매 단계 충족):
- 응답 가용성 유지
- **취소 인프라 실패율 0%**(정상 경쟁인 404·409는 제외)
- 정합성 위반 및 `settlement_batch_fallbacks_total` 0
- 회복 성능 악화 없음

**현재 단계**: ✅ **A+C 완료 + 29번 GCP 재측정으로 최종 판정 완료** →
[29번 GCP 스케일 최종 판정](../benchmarks/29-2026-07-30-per-order-fence-gcp-remeasurement.md).
**파티션 전체 fence는 제거됐고 바인딩 링크가 "fence 대기"에서 "정산 워커·DB 처리 용량(N=4)"으로
이동했다** — worker busy 13.1%→99.95%, 정산 처리율 ≈109→≈372 trades/s, 업무 성공률
10.82%(26번)→22.70%. 정합성·무결성 전항목 통과, 가용성·취소 하드 보장 유지.
**단, 28번이 "배리어가 배치 누적을 가로막는다"고 설명한 평균 배치 2.8은 fence 제거 후에도 2.78로
그대로여서 그 인과 주장은 반증됐다.** 대신 **terminal 경계가 batch run length를 제한한다는 새 가설**이
수치상 강하게 지지된다(`collectTradeBatch`가 비-trade 이벤트에서 배치를 끊고, terminal이 전체 이벤트의
31.9%다 — 독립 혼합 가정 아래 근사 `1/0.319≈3.13` vs 관측 2.78~2.83). **가설이지 확정된 인과가 아니며,
실제 연속 trade run-length 분포를 다음 측정에서 직접 계측해 확인해야 한다.**

**남은 것은 축 2뿐이 아니다.** 다음 두 갈래를 **병렬이 아니라 독립 순서로** 관리한다 —
서로 판정을 섞지 않는다:

1. **축 1 후속 — terminal 경계 배치 파편화 진단**(진단 선행: run-length 분포, job 종류별 실행 시간
   분리, terminal의 DB transaction 비중). **`N=4 → 8` 통제 비교는
   [30번](../benchmarks/30-2026-07-31-settlement-concurrency-sweep.md)에서 완료했다 — 결과는 기각.**
2. **축 2 — 매칭 quantum**(최악 fan-out에서의 진행성, 계약 6개 선결)

**30번 결과 요약**: N=4가 29번을 6개 지표 전부 허용 오차 내로 재현해(최대 편차 −0.9%) **단일 실행
A/B가 성립함을 처음 확인**했다. N=8은 hold 처리율 **+26.9%**(368→467 trades/s), 업무 성공률
**22.43%→26.62%**로 이득이 실재했지만, **`sli_order_response_availability`가 100.00%→99.94%로
떨어져(1,079,484건 중 568건이 1초 계약 초과) 안전 게이트에 걸려 기각**했다. 정합성은 양쪽 다 무결
(위반·fallback·quarantine·duplicate 전부 0, 취소 100%, 5xx 0). **병목은 정산 워커에서 DB CPU로
이동**했다(hold `us+sy` p95 61→84, recovery 68→99; `wa`≤9·`st`≤2로 스토리지·호스트 경합 아님).
**초기 풀 고갈은 악화되지 않았고**(setup `wait_count` −0.1%, 부하 구간 `in_use` 최대 12/25)
**풀 크기 25는 원인이 아니다.** 평균 배치는 2.764→2.790으로 **동시성을 2배로 해도 커지지 않았다** —
배치 파편화 진단의 필요성이 더 뚜렷해졌다.

**기각의 범위**는 "N=8 자체가 나쁘다"가 아니라 **"현재 DB 4 vCPU 구성에서는 N=8의 처리율 이득이
응답 가용성 계약을 깨므로 채택할 수 없다"** 이다. 또한 **재현 게이트에 지연이 없었다** — 동일 구성인
29번과 30번 N=4의 p95가 **약 35% 차이**(120.5 → 162.7ms)나므로 **지연의 run-to-run 분산은 처리율보다
크고, p95 단독 비교로 개선/회귀를 주장할 수 없다**(N=8 기각은 p95가 아니라 두 번 연속 0이던 1초 초과
건수가 568로 뛴 것에 근거한다).

**31번 결과 — DB 인스턴스 증설로 N=8을 안전하게 회수했다**
([31번](../benchmarks/31-2026-07-31-db-instance-scaleup.md), DB `e2-highcpu-4`→`e2-highcpu-8`,
4 vCPU/4 GB → 8 vCPU/8 GB, 인스턴스 ID·디스크 유지):

- **1차 안전 게이트: DB8/N4·DB8/N8 양쪽 모두 1초 초과 0건.** 30번 DB4/N8을 기각시킨 568건이
  **0건**으로 돌아왔다. 정합성·fallback·quarantine·duplicate 전부 0, 취소 100%, 5xx 0.
  **두 실행 모두 그 실행의 최종 데이터로 리컨실리에이션을 완주**시켜 4항목 0을 확인했다
  (30번에서 N=4 쪽을 놓쳤던 항목을 이번엔 양쪽 다 확보).
- **2차 효과 게이트 통과**: DB8/N4 대비 hold 처리율 **480.92→644.16 trades/s(+33.9%)**,
  업무 성공률 **26.51%→32.05%(+5.54%p)**, 절대 하한(30번 DB4/N8)도 충족 → **DB8 + N=8 채택 후보.**
- **runbook의 예상이 빗나간 지점**: "N=4는 worker 포화라 DB만 키워도 거의 안 변할 수 있다"고 했지만
  **DB8/N4만으로 hold +30.6%**(368→481)였다. attempt 시간이 14.19→10.59ms로 줄어 같은 포화에서 더
  처리했다. 그 결과 **DB8/N4가 이미 DB4/N8을 체결 수에서 추월**했다(167,128 vs 163,836).
- **병목이 DB CPU에서 서버 CPU로 이동**했다 — DB hold `us+sy` p95 **84→49**, 서버 **76→85**
  (burst p95 90). `wa`≤5·`st` 0.
- **풀 크기 25는 이번에도 제약이 아니다**(부하 구간 `in_use` 최대 12/25). setup 구간의 누적 대기는
  DB를 두 배로 키워도 거의 안 변했다(26.6k→26.4k) — **DB 속도가 아니라 풀 상한과 계정 생성 버스트의
  관계**에서 나온다.
- **평균 배치는 2.776→2.760으로 또 안 움직였다** — fence 제거(29)·동시성 2배(30)·DB 증설(31)
  **세 번 연속**이다.

**결론의 범위**: CPU와 RAM이 함께 늘고 실행 호스트도 바뀌므로 **"DB 인스턴스 증설 효과"** 이지
CPU 단독 효과가 아니다. DB4 기준값은 다른 세션·호스트에서 얻은 값이라 호스트 분산이 섞여 있다
(단 DB8/N4↔DB8/N8은 같은 세션·호스트라 2차 게이트 판정에는 이 오염이 없다).

**32번 — 용량 경계 탐색·확증(완료)**
([32-A](../benchmarks/32-2026-08-01-capacity-boundary-session-a.md) ·
**[32-B(최종 판정)](../benchmarks/32-2026-08-01-capacity-boundary-session-b.md)**): 증설 순서를 정하기 전에
**"지금 구성이 100%를 유지하는 최대 부하가 얼마인가"** 를 먼저 재기로 했다. 기존 벤치마크는
일부러 포화시키는 스파이크라 계단 사이에 측정점이 없었다(확정된 것은 "10,000 미만"뿐).

- **최종 결과(32-B): 이 워크로드와 현재 구성에서 유한 실행으로 검증된 최고 VU = 합산 500**
  (10분 hold, **2회 반복 통과**). **750은 10분 hold에서 업무 성공률 93.48%로 실패**(셰딩 36,989).
  runbook의 고정 분기대로 750을 평균 없이 탈락시키고 500으로 내려가 2회 확증했다.
- **세션 A의 "3분 750 통과"는 세션 B에서 뒤집혔다.** 750의 셰딩은 **hold 4.2~4.4분에 시작**하므로
  3분 hold는 포화 직전에 끝난다. 판정 정의를 10분 × 2회로 잡아 둔 것이 실제로 작동했다.
  아래 세션 A 관측은 **3분 구간의 거동**으로만 읽는다.
- **⚠ 고정 부하에서 정산 비용이 오른다 — 32-B가 새로 연 가장 큰 항목이다.** 부하가 일정한데도
  **작업당 정산 실행 시간이 hold 동안 9.19ms → 23.75ms(2.6배)로 오르고, 10분 안에 정상 상태에
  도달하지 않는다.** 배치 크기는 2.42→2.69로 평평하니 **파편화는 원인이 아니다**(29·30·31에 이은
  **네 번째 파편화 반증**). **그 이상은 미확정이다** — 원장 크기·인덱스·WAL/checkpoint/autovacuum·
  지갑 행 락 경합·job mix·오더북 변화 중 **어느 것도 배제되지 않았고, 더 오래 돌리면 평형점에
  도달하는지도 모른다.** 따라서 **"최고 검증 VU"는 hold 길이와 분리되지 않는다** — 500도
  **10분에 통과했을 뿐**, 같은 상승 추세를 보인다(**몇 분에 실패하는지는 측정하지 않았다**).
- **세션 A의 3분 관측(참고)**: 750 전 항목 100%/0건, 1,000은 업무 성공률 97.98%(셰딩 4,802건).
- **가장 먼저 깨지는 것은 업무 성공률(셰딩)이다.** 1,000에서도 응답 가용성 100% · 1초 초과 0건 ·
  취소 100% · 정합성 무결이었다 — 입장 게이트가 **지연을 키우는 대신 빠르게 503으로 셰딩**하는
  설계가 그대로 작동한 결과다. 셰딩 4,802건은 **전부 hold에서 발생**했고 ramp에서는 0건이라,
  경계가 **램프 과도현상이 아니라 지속 부하 현상**임이 확인된다.
- **최초 바인딩 신호는 N=8 정산 worker pool**이다: hold worker busy **65.04%(750) → 94.84%(1,000)**,
  dispatch wait 1.44ms → 9.77ms. 서버 CPU median 60→71(p95 74), DB 32.5→49, 풀 11/25로
  **헤드룸이 남아 있다.** **다만 "N=8의 한계"로 확정하지 않는다 — N=16 실험 전에는 원인을 확정할 수 없다.**
- **계단식 탐색은 실제로 오염됐다**: 계단식에서 1,000이 87.77%였는데 독립 실행에서는 97.98%였다.
  **상태 이월이 이번에는 후속 계단을 불리하게 만들었으나 구체적인 원인(백로그·오더북 성장·캐시)은
  분리하지 않았다.**
- **운영 신호**: 리컨실리에이션 실행시간이 데이터 증가폭보다 훨씬 크게 늘어나는 현상을 관측했다
  (체결 114,530건 약 5초 vs 362,654건 약 17.5분). 32-B에서 **체결 311,207건·사용자 750명 실행이
  30초**로 끝나면서 **체결 수 단독 설명은 배제**됐다(사용자 수 쪽이 지배적). **원인은 여전히 미확정**이며
  **우선순위 높은 진단 백로그**다. **정산 비용 상승과 섞지 않는다** — 리컨실리에이션은
  사용자·지갑별 LATERAL 집계라는 별도 쿼리로, 정산 경로와 비용 구조가 다르다.

**증설 순서 — 32-B가 세션 A의 판단을 무효화했다.** 세션 A는 "서버·DB에 헤드룸이 남고 워커만
포화되므로 `N=16`이 먼저"라고 적었으나, 그 판단은 **3분 관측의 DB CPU median 32.5%에 근거**했다.
**10분 실행에서 750이 실패하는 시점의 DB CPU median은 85%(p95 92)** 다. **원인이 락이나 WAL이면
`N=16`은 개선이 아니라 지연 악화를 만들 수 있다.** 따라서 `N=16`도 서버 VM 증설도 다음 후보가 아니다.

**다음은 고정 부하에서 정산 비용이 상승하는 원인 진단이다.** 두 단계로 간다 —
**(a) 정적 DB 조사**(인덱스 정의·사용량, autovacuum·dead tuple·checkpoint·WAL, 정산 SQL의
`EXPLAIN (ANALYZE, BUFFERS, WAL)`, `pg_stat_statements` 호출당 시간), **(b) 실제 `SettleTradeBatch`를
DB 크기 × 동시성(N=1/N=8)으로 스윕**. **N=1부터 느려지면 인덱스·WAL·쓰기 증폭, N=8만 느려지면
락·동시성 경합, 둘 다 평평하면 오더북·job mix·사용자 상태**로 갈린다.

> **⚠ `EXPLAIN`만으로는 닫히지 않는다** — 정산 경로의 중심은 INSERT·UPDATE·행 락·COMMIT·WAL이다.
> **load-gen 2대와 전체 k6 세션은 필요 없지만, 실제 트랜잭션을 돌리는 통제된 부하는 필요하다.**

증설은 그 뒤에 판단한다. **진단이 동시성 부족을 가리킬 때만** 아래로 간다:

1. **N=16에서 동일 경계 탐색**(10분 hold 기준, 32-B의 500이 비교 기준선)
2. **10,000 hold · 20,000 burst 포화 프로파일에서 안전 게이트 재검증**
3. **두 조건을 모두 통과해야 N=16 채택**

**3번을 빼면 안 된다** — [30번](../benchmarks/30-2026-07-31-settlement-concurrency-sweep.md)에서
N=8이 DB4 구성의 포화 프로파일에서 1초 계약을 깬 전례가 있다. **경계 부근에서 안전한 것과
포화에서 안전한 것은 다른 질문이다.**

- 28번(GCP 스케일 관측성 재측정)이 27번의 정산 큐 포화(`worker="8"`=256 cap)를 정확히 재현하고
  **파티션 전체 fence가 지배적**이라고 판정(hold 구간 `market_done` 배리어 wait duty 52.3%, 배리어
  진입 시 in-flight 항상 1)한 뒤, 그 fence를 주문별로 좁히는 A(런타임 fence)를 설계하려던 중
  **더 근본적인 정합성 구멍**을 발견했다: `SettlementRetryWorker.retryFailedCompletions`가 그
  주문의 미해결 failed settlement를 확인하지 않아 **미정산 trade 위에서 시장가 완료가 실행**되고
  잔여 홀드를 잘못 반환할 수 있었다. A를 먼저 넣어도 실패 순간엔 이 순서 위반이 그대로 성립하므로,
  **B를 먼저 닫아 "복구 경로는 순서를 지킨다"는 전제를 확보**했다(성능과 무관한 독립 버그 수정).
- B: `HasOpenFailureForOrder`(DB EXISTS)를 repository→service→워커 네 계층에 통과시켜, 같은 주문을
  참조하는 `OPEN` failed settlement가 있으면 시장가 완료 terminal을 durable defer한다. dependency
  store가 nil이거나 조회 오류면 phase 단위 fail-closed(이번 사이클 completion 전체 중단). 차단은
  `settlement_completion_blocked_total` 카운터로만 관측(로그 없음).
- **A+C 완료**: dispatcher의 파티션 전체 배리어를 `dependencyTracker`(주문ID→미retire 배치 수) 기반
  주문 단위 fence로 축소 — 28번이 실측한 "무관한 주문의 배치까지 막히는" 문제를 직접 해소했다.
  취소 terminal에도 시장가 완료와 동형의 durable defer 계약(`FailedOrderCancellation`,
  `RecordFailure`/`EnsureDeferred` 구분, `retry_count=0` 시작)을 갖췄다. 배리어 지표
  (`settlement_barriers_total` 등)를 제거하고 `settlement_terminal_wait_seconds`/
  `settlement_outstanding_jobs`/`settlement_quarantined_orders`/
  `settlement_dependency_record_failed_total`로 교체. 자세한 내용과 대화 중 정정된 사항은
  [22번 완료 문서](22_4차_축1_per-order_fence_완료.md) 참고.
- **29번 GCP 실측 완료**(측정 기준 SHA `82b4d7f`,
  [runbook](../superpowers/plans/2026-07-30-per-order-fence-gcp-remeasurement.md) →
  [결과](../benchmarks/29-2026-07-30-per-order-fence-gcp-remeasurement.md)): 폐기한 배리어 지표가
  실제로 사라지고 신규 5종이 정상 동작함을 확인, 계측 내부 무결성 9항목이 오차 0으로 일치했다.
  주의: runbook의 주 가설 기준("terminal wait p50 감소")은 **28번 barrier wait과 측정 대상이 달라
  직접 비교가 성립하지 않는다** — fence 제거 판정은 처리량 지표를 근거로 했다.

## 리뷰에서 나왔지만 채택하지 않은 것

- **MSA 전환**: 매칭 엔진의 본질이 심볼당 단일 스레드 직렬화라 분산해도 병렬화되지
  않음. 모듈러 모놀리스 유지. 유일한 분리 후보는 WS market-data fanout(B-1 이후 재판단).
- **Kafka**: 단일 브로커는 Postgres COMMIT 대비 추가 내구성이 0인데 dual-write 문제를
  새로 만듦. A-3의 transactional outbox가 정석 관문(추후 CDC로 전환 경로 열림).
- **Redis**: 단일 프로세스에선 `atomic.Value`(인프로세스)가 항상 우월. WS를 다중
  인스턴스로 분리하는 시점에 pub/sub으로 첫 도입.
