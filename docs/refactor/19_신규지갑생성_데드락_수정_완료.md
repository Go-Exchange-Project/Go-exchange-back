# 19. 신규 지갑 생성 데드락 수정 — 완료

- **완료일**: 2026-07-27
- **근거**: [25번 재측정](../benchmarks/25-2026-07-27-settlement-parallelization-remeasurement.md)이
  `GOEXCHANGE_SETTLEMENT_CONCURRENCY=4`에서 1건, `=8`에서 4~6건의 Postgres 데드락
  (SQLSTATE 40P01)을 실측하고, goroutine 덤프로 `WalletRepository.CreateZeroBalanceWallets`를
  지목했다. README 백로그의 "신규 지갑 생성 시 비결정적 INSERT 순서로 인한 PostgreSQL
  데드락 (가설)" 항목이 이 사이클의 출발점이다.

## 왜 필요했나

`SettlementService.SettleTradeBatch`(`internal/service/settlement_batch.go`)는 배치 안에서
새로 만들어야 하는 지갑 목록(`missingCreatable`)을 Go map 순회로 구성한 뒤
`WalletRepository.CreateZeroBalanceWallets`(여러 행을 한 INSERT 문으로 배치 삽입)에 그대로
넘기고 있었다. Go map 순회 순서는 호출마다 무작위라, **겹치는 신규 지갑 키를 서로 다른
트랜잭션이 동시에 생성하면 그 배치 INSERT 문 안의 행 순서가 트랜잭션마다 달라질 수 있다** —
PostgreSQL은 이런 경우 튜플 락 순환(circular wait)을 감지해 데드락으로 한쪽을 강제 abort한다.
같은 파일의 주문 락(`sortedUintKeys(orderIDSet)`)·지갑 락(`sortedUintKeys(walletIDSet)`)은
이미 오름차순 정렬이 돼 있었는데, **INSERT 단계만 정렬이 빠져 있었다**.

## 어떻게 해결했나(TDD)

### 1. RED — 재현

`internal/service/settlement_new_wallet_deadlock_integration_test.go` 신규:
`TestIntegrationConcurrentNewWalletCreationDoesNotDeadlock`. 매 라운드(30회) 신규 유저 2명
(A: KRW만, B: 코인만 보유 — crossing-flood.js 픽스처와 동일 구성)을 만들고, **같은 A/B
역할의 독립된 주문쌍 2개**를 서로 다른 `SettleTradeBatch` 트랜잭션에서 동시 호출한다. 두
트랜잭션 모두 정확히 같은 신규 지갑 키 집합(`A:BTC`, `B:KRW`)을 생성해야 하므로 최대로
겹친다.

수정 전 실행 결과, 정확히 가설대로 재현됐다 — 두 트랜잭션의 INSERT `VALUES` 행 순서가
문자 그대로 뒤집혀 있었다:

```
INSERT INTO "wallets" (...) VALUES ('0','BTC',...,U1),('0','KRW',...,U2) ON CONFLICT ... DO NOTHING
INSERT INTO "wallets" (...) VALUES ('0','KRW',...,U2),('0','BTC',...,U1) ON CONFLICT ... DO NOTHING
ERROR: deadlock detected (SQLSTATE 40P01)
```

30라운드 중 3건(수정 전 로컬 실행 기준)이 재현됐다 — 재현이 확률적(Go map 순회 무작위성에
의존)이라 라운드 수를 충분히 확보해 안정적으로 잡히게 했다. 리뷰가 정렬 코드만 되돌려
독립 재현(5건/30라운드)했고, 복원 후 3회 연속 GREEN을 재확인했다.

### 2. 최소 수정

`missingCreatable` 구성 직후, `CreateZeroBalanceWallets` 호출 직전에 `(UserID, CoinSymbol)`
오름차순 정렬 한 줄을 추가했다(`sortedUintKeys`와 같은 목적, 같은 파일에 이미 있던 패턴):

```go
sort.Slice(missingCreatable, func(i, j int) bool {
    if missingCreatable[i].UserID != missingCreatable[j].UserID {
        return missingCreatable[i].UserID < missingCreatable[j].UserID
    }
    return missingCreatable[i].CoinSymbol < missingCreatable[j].CoinSymbol
})
```

정산 로직·주문/지갑 락 순서·멱등·폴백은 전혀 건드리지 않았다(`internal/service/settlement_batch.go`
+9줄만 추가, 삭제 0). **정렬 기준이 Postgres 유니크 인덱스 컬럼 순서와 일치하기 때문이 아니라
(실제 인덱스는 `btree (coin_symbol, user_id)`로 반대다), `(UserID, CoinSymbol)`이 중복 없는
결정론적 전순서이고 모든 트랜잭션이 같은 순서로 락을 요청하게 만들기 때문에 충분하다** — 두
자원이 반대 순서로 요청되는 조합(`k1<k2`이면서 `k2<k1`)이 성립할 수 없어 순환 대기 자체가
불가능해진다.

## 주장의 범위 — 정직하게

**정렬이 모든 정산 데드락을 없앤다고 주장하지 않는다.** 이번 수정은 "신규 지갑 생성
배치 INSERT의 행 순서 불일치"라는 **한 가지 클래스**만 없앤다. `SettleTradeBatch`의 다른
단계(주문 락, 지갑 락, 배치 UPDATE)는 이미 정렬돼 있었거나(락 단계) 락을 이미 보유한
뒤라 위험이 없음을 확인했다(8단계 배치 UPDATE의 map 순회는 3·6단계에서 해당 행 락을 이미
전부 쥔 상태이므로 안전). N=8 등 더 높은 동시성에서 fallback/40P01이 남아 있다면, 이번
수정과 무관한 다른 락 경로일 수 있으므로 SQLSTATE와 goroutine/DB 로그로 재분류해야 한다 —
이번 사이클에서는 N=8 재측정을 반복하지 않았다(짧은 사이클 범위는 N=4 확인까지).
